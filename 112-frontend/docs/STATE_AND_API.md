# Решение по состоянию и API

Проверено и переработано 22.09.2026. TanStack Query и Zustand уже были подключены,
но АРМ хранил несколько копий серверной попытки и собственную очередь Promise.
Теперь эти механизмы заменены возможностями библиотек.

| Ответственность | Решение | Текущее место |
| --- | --- | --- |
| Серверные списки, детали, ошибки, фоновые обновления | TanStack Query | `app/providers/QueryProvider.tsx`, `useQuery` / `useMutation` в моделях и страницах |
| HTTP, токены, единичный повтор после refresh | ky | `shared/api/backendApi.ts`, `entities/*/api` |
| Сеанс, токены и восстановление вкладки | Zustand + persist | `entities/user/model/authStore.ts` |
| Значения и валидация формы входа | React Hook Form | `features/auth/model/useLoginForm.ts` |
| Несохранённый черновик, выбранная плитка, открытый диалог | Локальное состояние React | Модель соответствующего слайса |

TanStack Query управляет серверным состоянием и вызывает переданную асинхронную
функцию. Он не заменяет HTTP-клиент, контракт API, восстановление сеанса или
валидацию формы. Zustand нужен для общего клиентского состояния; переносить в
него списки пользователей, карточек и занятий означало бы вручную повторить кэш
и инвалидацию Query. Такое разделение соответствует
[рекомендации TanStack](https://tanstack.com/query/latest/docs/framework/react/guides/does-this-replace-client-state)
и [модели Zustand](https://github.com/pmndrs/zustand#readme).

## Что уже сделано в приложении

- `QueryProvider` создаёт один стабильный QueryClient. По умолчанию staleTime —
  10 секунд, повторы запросов отключены; polling задаётся конкретным запросом.
- Пользователи, каталоги, занятия, оценки, сообщения и генерация используют Query.
- Попытка имеет один ключ `trainingKeys.attempt(id)`. Журнал, оператор 112 и ДДС
  наблюдают один Query-кэш. `queryOptions` объединяет ключ, запрос и AbortSignal;
  повторное открытие свежей карточки использует кэш. Старт карточки — mutation,
  её чтение и повторное чтение — query. При истечении срока инвалидируется этот ключ.
- Ответы сохранения/сдачи сразу попадают в кэш через `setQueryData`. Перед записью
  отменяется незавершённое чтение, чтобы старый GET не затёр новую ревизию.
- Последовательность автосохранения, ручного сохранения и сдачи обеспечивается
  одинаковым `scope.id` mutations. Ревизия берётся из кэша в момент исполнения.
  Собственная цепочка Promise и дублирующие refs ревизии удалены. Дебаунс ввода,
  отсчёт времени и несохранённые поля остаются локальной логикой формы.
- Zustand теперь хранит и tokens, и поколение сеанса. `persist` сохраняет только
  tokens в sessionStorage; session/roles/status/generation не восстанавливаются
  из хранилища. Используется стандартный JSON storage без адаптера старого формата;
  после обновления старого сеанса нужен повторный вход. При выходе ключ
  удаляется через persist; параллельного изменяемого token-кэша больше нет.
- `AuthProvider` очищает кэш при смене пользователя. Обновление access token
  объединяет параллельные запросы и проверяет поколение сеанса, чтобы ответ старого
  пользователя не восстановил сеанс после выхода. Это часть протокола авторизации,
  а не альтернативная реализация TanStack Query.
- Формы авторизации используют React Hook Form; его `isSubmitting` уже управляет
  отправкой. Дополнительный mutation только ради второго индикатора отправки
  здесь не нужен.
- Очереди аудита и прокторинга решают доставку упорядоченных событий с повторами;
  их нельзя заменить обычным кэшем запросов без потери этих гарантий.

## Правила дальнейшей разработки

1. Новый серверный read — через `useQuery`, запись — через `useMutation`, если это
   действие обычного экрана. Не создавать рядом свои `loading/data/error` и polling.
2. HTTP-функции остаются в `api`, query options / ключи / hooks — в `model` своего
   слайса, типы — в `types`, UI — в `ui`. Общий транспорт не импортирует сущности.
3. Переиспользуемые query keys и options выносить при появлении нескольких
   потребителей; после записи обновлять или инвалидировать соответствующий кэш.
4. Передавать AbortSignal в HTTP-запросы. Повторы записей включать только при
   поддерживаемой сервером идемпотентности.
5. Zustand не дублирует Query-кэш. Локальные поля формы не становятся глобальным
   store, если ими не нужно совместно управлять из разных частей приложения.

Модели рабочего места вынесены в `pages/training-workspace/model`; UI больше
не управляет запросами, очередью и локальной копией ответа. В других страницах
query hooks ещё встречаются непосредственно в UI; их следует выносить при
доработке соответствующего процесса. Неиспользуемый старый `LocationMap` удалён при повторном проходе ниже.

## Удаление дублирующего кода и области контекстов

Повторный проход 22.09.2026:

- `useIncidentEditor` использует mutation для команды формы (аудит → сохранение
  → при необходимости сдача). Удалены собственные `pending/error/saved`,
  `savedFields` и два блока `try/catch/finally`. Результат и состояние команды
  читаются из mutation. Несохранённые поля остаются локальным состоянием формы.
- Удалён неиспользуемый локальный workflow: чтение/запись/миграция карточек в
  localStorage, локальная проверка заполнения, фиксированные признаки и выбор
  служб старого прототипа. Все текущие вызовы редактора используют API-контракт.
  Существующие серверные ответы, комментарии, ручной выбор служб и автосохранение
  сохранены. Тесты удалённого хранилища удалены вместе с ним.
- Импорт ЕКП показывает `mutation.error`, без отдельной копии ошибки в useState.
- Удалён неподключённый `location-map-placeholder` с собственными fetch,
  AbortController и loading/error. Активный `LocationPicker` с Яндекс.Картами
  сохранён; его жизненный цикл относится к экземпляру карты в DOM.
- `IncidentCardStoreProvider` существует внутри одной формы: адрес, телефоны,
  признаки и диалог служб читают нужный срез `editor`/`disabled` через Zustand,
  без передачи общей модели через промежуточные компоненты.
  `DDSWorkspaceStoreProvider` так же изолирует нижнюю панель, историю и форму
  статуса в пределах одной карточки ДДС. Store создаётся на экземпляр диалога,
  не persist-ится и не смешивает черновики двух карточек; порталы MUI сохраняют
  его область. Глобальный Zustand-store для этих форм намеренно не используется.
- Props остаются для индивидуальных параметров отображения и событий компонента.
  Контексты не добавляют второй кэш API и не переносят состояние карточки в
  глобальную переменную. Их типы находятся в `types`, context/hooks — в `model`.

### Сопоставление с CAVISE/scenario-manager

Изучен GitHub `main` на коммите `9854eb6c6a4012115b2c743298baf7b758b3f701`,
а не только более старый локальный checkout:

- [HooksProvider](https://github.com/CAVISE/scenario-manager/blob/9854eb6c6a4012115b2c743298baf7b758b3f701/frontend/src/pages/editor/context/HooksProvider.tsx)
  объединяет функции редактора;
  [EditorRefsProvider](https://github.com/CAVISE/scenario-manager/blob/9854eb6c6a4012115b2c743298baf7b758b3f701/frontend/src/pages/editor/context/EditorRefsProvider.tsx)
  задаёт область ресурсов сцены. Для 112 полезен именно принцип области одного
  редактора, применённый выше.
- [useEditorStore](https://github.com/CAVISE/scenario-manager/blob/9854eb6c6a4012115b2c743298baf7b758b3f701/frontend/src/store/useEditorStore.ts)
  использует Zustand persist/partialize для состояния редактирования.
  В 112 общее состояние сеанса уже хранится в Zustand; черновики отдельных
  открытых карточек остаются изолированными.
- [useScenarioQueries](https://github.com/CAVISE/scenario-manager/blob/9854eb6c6a4012115b2c743298baf7b758b3f701/frontend/src/pages/editor/hooks/useScenarioQueries.ts)
  группирует query keys и mutations с обновлением/инвалидацией кэша.
  Там queryFn также записывает полученный сценарий в store. В нашем редакторе
  фоновые ответы не должны перезаписывать несохранённый ввод, поэтому этот
  конкретный приём не переносится.

Наличие нескольких предметных hooks само по себе не является дублированием.
Проверяем ответственность: один механизм загрузки/ошибок/кэша, одна модель формы,
контекст только для совместных потребителей в её дереве. Очереди наблюдений,
объединение refresh и защита от ответа прежнего сеанса остаются частью протокола.
