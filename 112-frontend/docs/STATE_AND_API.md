# Решение по состоянию и API

Проверено по исходникам 22.09.2026. Оставляем TanStack Query и Zustand:
обе библиотеки уже подключены и используются, повторная интеграция не нужна.

| Ответственность | Решение | Текущее место |
| --- | --- | --- |
| Серверные списки, детали, ошибки, фоновые обновления | TanStack Query | `app/providers/QueryProvider.tsx`, `useQuery` / `useMutation` в моделях и страницах |
| HTTP, токены, единичный повтор после refresh | ky | `shared/api/backendApi.ts`, `entities/*/api` |
| Сеанс и доступ к нему из разных частей приложения | Zustand | `entities/user/model/authStore.ts` |
| Значения и валидация формы входа | React Hook Form | `features/auth/model/useLoginForm.ts` |
| Несохранённый черновик, выбранная плитка, открытый диалог | Локальное состояние React | Модель соответствующего слайса |

TanStack Query управляет серверным состоянием и вызывает переданную асинхронную
функцию. Он не заменяет HTTP-клиент, контракт API, восстановление сеанса или
валидацию формы. Zustand нужен для общего клиентского состояния; переносить в
него списки пользователей, карточек и занятий означало бы вручную повторить кэш
и инвалидацию Query. Такое разделение соответствует
[рекомендации TanStack](https://tanstack.com/query/latest/docs/framework/react/guides/does-this-replace-client-state)
и [модели Zustand](https://github.com/pmndrs/zustand#readme).

## Что уже сделано в приложении

- `QueryProvider` создаёт один стабильный QueryClient. По умолчанию staleTime —
  10 секунд, повторы запросов отключены; polling задаётся конкретным запросом.
- Пользователи, каталоги, занятия, оценки, сообщения и генерация используют Query.
- `AuthProvider` очищает кэш при смене пользователя. Обновление access token
  объединяет параллельные запросы и проверяет поколение сеанса, чтобы ответ старого
  пользователя не восстановил сеанс после выхода. Это часть протокола авторизации,
  а не альтернативная реализация TanStack Query.
- Формы авторизации используют React Hook Form; его `isSubmitting` уже управляет
  отправкой. Дополнительный mutation только ради второго индикатора отправки
  здесь не нужен.
- Очереди аудита и прокторинга решают доставку упорядоченных событий с повторами;
  их нельзя заменить обычным кэшем запросов без потери этих гарантий.

## Правила дальнейшей разработки

1. Новый серверный read — через `useQuery`, запись — через `useMutation`, если это
   действие обычного экрана. Не создавать рядом свои `loading/data/error` и polling.
2. HTTP-функции остаются в `api`, query options / ключи / hooks — в `model` своего
   слайса, типы — в `types`, UI — в `ui`. Общий транспорт не импортирует сущности.
3. Переиспользуемые query keys и options выносить при появлении нескольких
   потребителей; после записи обновлять или инвалидировать соответствующий кэш.
4. Передавать AbortSignal в HTTP-запросы. Повторы записей включать только при
   поддерживаемой сервером идемпотентности.
5. Zustand не дублирует Query-кэш. Локальные поля формы не становятся глобальным
   store, если ими не нужно совместно управлять из разных частей приложения.

Найдены отдельные места для последующей декомпозиции: query hooks ещё встречаются
непосредственно в UI, снимок попытки хранится в моделях АРМ рядом с черновиком.
Их следует разделять при доработке соответствующего процесса, не затирая
несохранённый ввод фоновым refetch. Неиспользуемый в текущих страницах старый
`LocationMap` также содержит ручной fetch геокодирования; при его возвращении
запрос нужно перенести в Query. Это не основание переписывать весь слой API.
