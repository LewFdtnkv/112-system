# Авторизация через API

Фронтенд использует существующий backend без изменения его схемы и правил.
Базовый URL — `/api/v1`; его можно переопределить через `VITE_API_URL` при сборке.
Nginx из backend Compose проксирует `/api/` в API. Для Vite в Docker прокси по
умолчанию обращается к `http://host.docker.internal:8000`; адрес меняется через
серверную переменную `API_PROXY_TARGET`.

## Контракт и поведение

| Запрос | Назначение |
| --- | --- |
| `POST auth/login` | JSON `username`, `password`; получает пару токенов |
| `GET users/me` | Профиль и независимые флаги `is_teacher` / `is_admin` |
| `POST auth/refresh` | JSON `refresh_token`; ротация пары при HTTP 401 |
| `POST auth/change-password` | Bearer и JSON `current_password`, `new_password` |
| `POST auth/logout` | Bearer; отзыв текущей сессии |

Логин — 1–50 латинских букв, цифр, точек, дефисов и подчёркиваний. Email не служит
идентификатором входа. Пароль передаётся без обрезки пробелов. Новый пароль —
12–128 символов, отличается от текущего, не состоит только из пробелов;
повторный ввод проверяется до отправки.

При `must_change_password` разрешена только форма смены пароля и выход.
`users/me` до смены не вызывается. Ошибка `password_change_required` от защищённого
API также переводит на эту форму. После смены сохраняется новая пара токенов.

Токены сохраняются в `sessionStorage` под `dds112-tokens-v1`, чтобы восстановить
сеанс при перезагрузке вкладки. Пароли, профиль и права туда не записываются.
Права восстанавливаются по профилю сервера; старые демонстрационные записи
`dds112-auth` в localStorage удаляются. Приложение не использует HttpOnly-cookie:
существующий backend возвращает bearer-токены в JSON.

Истёкший access обновляется при HTTP 401. Параллельные запросы ожидают одну
операцию refresh, исходный запрос повторяется один раз. HTTP 401 от refresh
очищает сессию; сетевые ошибки и 5xx при восстановлении показывают повторную
попытку. Запоздавший ответ прежнего аккаунта не восстанавливает его сессию.
Выход отзывает сессию на сервере; локальные токены очищаются и при ошибке выхода.
QueryClient очищается при смене пользователя и выходе.

Администратор без `is_teacher` не получает кабинет преподавателя и учебные
разделы. При обоих флагах доступны оба кабинета. При отсутствии этих флагов
используется ученический кабинет. Это системные права, не учебные мини-роли.

## Границы интеграции

Подключены авторизация и прикладной процесс оператора 112, подготовка занятий,
управление пользователями, ручная оценка и аналитика. См. [API.md](API.md).
Демонстрационный транспорт и переключатель `VITE_USE_FAKE_API` удалены.
Подмена ответов API используется только в тестах.

Слои: транспорт и повтор запроса — `shared/api/backendApi`, DTO и жизненный цикл
сессии — `entities/user`, формы — `features/auth`, экраны — `pages`, восстановление
и очистка query-кэша — `app/providers/AuthProvider`.

## Области нажатия и выделение

Плитки навигации — целые нативные ссылки с внутренними отступами. У бокового
меню исправлена ширина, поэтому край пункта не перекрывается соседним экраном.
Сохраняются клавиатура, focus и hover. Статические элементы карточек имеют
`user-select: none` и префиксы `-webkit-`, `-moz-`, `-ms-`. Для редактируемых
`input` и `textarea` сохраняется `user-select: text`.

## Проверки в Docker

Из каталога frontend:

```sh
docker run --rm -v "$PWD":/app -v system112-design-node-modules:/app/node_modules -w /app node:24-bullseye-slim npm run build
docker run --rm -v "$PWD":/app -v system112-design-node-modules:/app/node_modules -w /app node:24-bullseye-slim npm run lint
docker run --rm -v "$PWD":/app -v system112-design-node-modules:/app/node_modules -w /app node:24-bullseye-slim npm test -- --maxWorkers=2
docker run --rm -v "$PWD":/app -v system112-design-node-modules:/app/node_modules -w /app -e PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH=/ms-playwright/chromium-1234/chrome-linux/chrome mcr.microsoft.com/playwright:v1.62.1-noble npm run test:e2e -- --workers=2 --grep-invert 'real API:'
```

`e2e/auth-real.spec.ts` запускается только при `AUTH_ISOLATED_API=true`, с
`API_PROXY_TARGET`, указывающим на отдельный backend со свежей временной БД.
Этот сценарий заменяет начальный пароль администратора и создаёт тестового
ученика, поэтому его нельзя направлять на рабочую БД. Обычные браузерные тесты
перехватывают только auth-запросы и не требуют учётных данных пользователя.

Проверяются неверный пароль, обязательная смена, обновление и отзыв токенов,
восстановление страницы, независимые права, нажатия у границ ссылок и запрет
выделения статического содержимого. Снимки находятся в `test-results`;
проверенные примеры — в `docs/screenshots/auth-*.png`.
