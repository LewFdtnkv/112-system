# Оптимизация API и повторные нагрузочные проверки

Дата: 27.09.2026. Предыдущие результаты сохранены в [RESULTS.md](RESULTS.md).

## Изменения

- Проверка сроков больше не загружает все JSON-снимки попыток класса при каждом действии.
  Прогресс вычисляется SQL-агрегацией, полные попытки нужны только для истёкших сроков.
  Изменение присутствия не инициирует проверку итоговых оценок всех незавершивших учеников.
- При массовой доставке ДДС исполнение ученика и версия сценария переиспользуются внутри
  одной операции. Долгоживущего кэша нет, расписание и серверные блокировки сохранены.
- Кабинет ученика выполняет три запроса вместо повторных выборок для каждого блока.
  История и страницы по-прежнему ограничены; изменения оценок видны следующим запросом.
- Авторизация читает пользователя и его сессию одним JOIN. Проверки отзыва сессии,
  отключения аккаунта и роли продолжают обращаться к БД на каждом запросе.
- API использует четыре процесса Uvicorn при общей квоте 4 CPU. Журнал HTTP использует
  [ConcurrentRotatingFileHandler](https://github.com/Preston-Landers/concurrent-log-handler)
  для безопасной ротации общего файла несколькими процессами. Максимальный пул API —
  60 соединений, плюс до 30 у двух фоновых сервисов при лимите PostgreSQL 100.

## Методика

Отдельная БД `perf112`, по 4 CPU API и PostgreSQL, по 2 GiB RAM. Генератор на том же
Docker Desktop (10 CPU, 7,75 GiB), поэтому результаты не являются паспортной мощностью
будущего сервера. Рабочие пользователи, оценки и задания не изменяются.

Перед каждым профилем создаётся свежий набор: 100 учеников, 20 карточек на роль,
4000 назначений. Обычный интервал поступления ДДС — 60 секунд. ИИ и SIP выключены.

Baseline: образ прежнего API, один Uvicorn-процесс. Optimized: изменённый API, четыре
процесса. Обе версии используют **один и тот же новый генератор**. Старые 10-секундные
ступени из RESULTS.md не используются для вычисления относительного ускорения.

- Пользовательские цепочки: 20 и 100 учеников, половина 112 / половина ДДС,
  подключение 5 учеников/с, 90 с включая подключение, до 30 с на завершение запросов,
  паузы 1–3 с между действиями и presence каждые 15 с.
- Максимальный RPS: отдельная смесь чтений (20% профиль, 30% кабинет, 30% список
  занятий, 20% сообщения). Входы выполняются до измерения. Генератор допускает
  2000 незавершённых запросов и до 50 мс задержки диспетчеризации, включённой в latency;
  более старые поступления считаются пропущенными.
- Рабочий порог RPS: ошибки + пропуски ≤1%, p95 ≤2 с. Это слабее требования ТЗ
  «каждый ответ ≤2 с»: в пользовательских профилях приводится также максимум.
- Final JSON Locust снимается после завершения пользователей; CSV может не включать
  последние ответы между последним периодическим снимком и остановкой.


## Контроль корректности

Полный набор до нагрузочных прогонов: 633 теста прошли; после добавления проверки
журнала обязательный pre-commit с полным pytest также прошёл (634 теста). Дополнительные регрессии
проверяют бюджет запросов кабинета и отсутствие массовой переоценки при уходе ученика.
Отдельная проверка ротации запускает четыре процесса, записывает 400 разных событий
и проверяет наличие каждого события после нескольких ротаций.

Блокировка занятия сохранена: её удаление требует отдельной переработки транзакций
доставки, завершения, оценки и телефонии. Здесь сокращено время её удержания.

## 20 и 100 одновременно работающих учеников

| Версия | Сессии | Запросы | Ошибки | HTTP RPS | p95 | p99 | Максимум |
|---|---:|---:|---:|---:|---:|---:|---:|
| baseline | 20 | 1223 | 0 | 13.61 | 950 мс | 1900 мс | 3483 мс |
| optimized | 20 | 1458 | 0 | 16.25 | 47 мс | 150 мс | 640 мс |
| baseline | 100 | 1552 | 16 | 15.20 | 17000 мс | 24000 мс | 31321 мс |
| optimized | 100 | 6651 | 0 | 74.10 | 110 мс | 420 мс | 1112 мс |

Оба оптимизированных прогона прошли строгий HTTP-порог 2 с для **всех** измеренных
ответов, а также проверки сохранения данных и завершения обоих типов карточек.
При 100 сессиях успешно отправлены 477 карточек 112 и 88 карточек ДДС.
Это один 90-секундный прогон на конфигурацию, не длительная сертификация стабильности.
Число RPS — выполненные HTTP-запросы с пользовательскими паузами, не потолок сервера.

В baseline-100: 7 ответов 500 и 9 ответов 409. Логи подтверждают таймауты пула
SQLAlchemy 5+10/30 с; при затянувшихся запросах также перестаёт своевременно доходить
presence. Не все 409 являются независимыми ошибками правил: они появляются уже при
перегруженном выполнении. В optimized-100 таких отказов нет.

## Насыщение чтений

В open-loop серии по 20 с baseline проходит 50 и 100 RPS, optimized — 50, 100,
200 и 400 RPS. На 400 RPS у optimized нет ошибок/пропусков, p95 13 мс.
Выше этих значений результаты HTTPX нельзя напрямую считать потолком API:
при большом числе соединений генератор сам занимает одно ядро и пропускает отправки.
Например, optimized/1000 RPS пропустил 17482 из 20000 запланированных поступлений.

Поэтому дополнительно используется FastHttpUser без пауз, с 20/100 одновременными
читателями. Стартовая статистика сбрасывается после подключения пользователей;
ниже считаются только четыре маршрута чтения, без авторизации/служебной проверки.

| Версия | Читатели без пауз | Запросы чтения | Ошибки | RPS | p95 | p99 | Максимум |
|---|---:|---:|---:|---:|---:|---:|---:|
| baseline | 20 | 11994 | 0 | 184.81 | 210 мс | 270 мс | 1032 мс |
| baseline | 100 | 11079 | 0 | 180.96 | 1100 мс | 1600 мс | 3374 мс |
| optimized | 20 | 45582 | 0 | 702.31 | 61 мс | 130 мс | 558 мс |
| optimized | 100 | 31045 | 0 | 509.57 | 420 мс | 660 мс | 3559 мс |

Измеренный максимум пропускной способности этой смеси — **около 700 RPS**.
Увеличение числа ожидающих читателей с 20 до 100 не даёт прироста; 1000 RPS не
подтверждены. На optimized/20 API занимал около 384–389% CPU (квота 400%),
PostgreSQL около 67–74%, FastHttpUser около 25–27%. Здесь ограничение — CPU API,
а не мощность генератора или CPU PostgreSQL. Это максимум конкретной смеси чтений,
не пропускная способность записи, ИИ или телефонии.

При 100 читателях без пауз есть ответы дольше 2 с; это стрессовый тест с постоянной
очередью, в отличие от **100 работающих учеников**, для которых все ответы уложились
в норматив в измеренном прогоне. Не подменять один профиль другим.

## Цена и дальнейшие ограничения

- Четыре API-процесса занимают около 529 MiB вместо 153 MiB у одного процесса
  в пользовательском прогоне на 100 учеников. Квота CPU API и БД остаётся 4 каждому.
- Максимум ожидающих блокировку БД в этом профиле снизился с 14 до 3. Пул не расширяли
  внутри процесса; исчезла причина длительного удержания соединений.
- Следующее направление для RPS — CPU-профилирование построения SQLAlchemy-проекций,
  сериализации и HTTP middleware. PostgreSQL в измерениях не упирался в четыре ядра;
  увеличение его CPU или безусловное расширение пула само по себе не устранит предел API.
- Для более интенсивной массовой доставки ДДС остаётся общая блокировка занятия.
  Перенос на блокировки отдельного ученика потребует согласованно переработать все
  завершения, оценки, дедлайны и SIP callbacks; это отдельная задача, не безопасная
  механическая замена блокировки.
- Проверить production-объём истории/ЕКП, длительность 30–60 минут, ИИ/SIP вместе
  с пользователями и отдельный генератор нужно отдельно. Эти короткие прогоны
  подтверждают улучшение, но не заменяют такую проверку.

Сырые результаты: [results/2026-09-27-optimized](results/2026-09-27-optimized).
В репозиторий включены итоговые JSON/CSV и метрики ресурсов; манифесты с паролями
и полные журналы запросов остаются только в игнорируемой папке artifacts.

Оптимизации проверены на отдельном стенде. После отдельного подтверждения пользователя
рабочие API/worker/telephony-worker обновлены: readiness `ok`, frontend HTTP 200,
четыре процесса API, по 4 CPU у API и PostgreSQL. Счётчики сохранены: 9 пользователей,
30 карточек, 26 занятий, 8 итоговых оценок. Изменений схемы, паролей и seed нет.
