# Нагрузочные проверки System112

Набор отделён от runtime приложения: **Locust 2.43.3** для пользовательских цепочек,
**HTTPX 0.28.1** для потока с заданным RPS. Библиотеки устанавливаются только
в образ генератора. Рабочая БД, пароли demo-пользователей и очередь ИИ не используются.

## Ресурсы и ограничения

- В основном `compose.yaml` API и PostgreSQL имеют квоту **4 CPU каждый**
  (`API_CPUS` / `DB_CPUS`). В отдельном стенде те же квоты, по 2 GiB памяти.
- Квота CPU — верхний предел, а не закреплённые физические ядра. Для воспроизводимого
  прогона нужны ресурсы на API, БД **и генератор**; не запускайте другие тяжёлые проверки.
- API запускает четыре Uvicorn-процесса (`API_WORKERS`, в нагрузочном стенде
  `PERF_API_WORKERS`), каждый с пулом SQLAlchemy 5+10 соединений: максимум 60 для API.
  Два фоновых сервиса добавляют до 30 соединений; при увеличении числа процессов
  пересчитайте общий бюджет PostgreSQL (по умолчанию 100). Фоновые проверки сроков
  используют блокировки `SKIP LOCKED`, ротация журнала защищена межпроцессной блокировкой.
  Для сравнения с прежней версией используйте отдельный образ через `PERF_API_IMAGE`
  и `PERF_API_WORKERS=1`, без пересборки baseline-образа.
- ИИ и SIP на этом стенде отключены. Запрос постановки ИИ-задачи в очередь не равен
  завершению генерации/оценивания; задержка VoIP не измеряется HTTP-инструментом.
- `seed` проверяет имя БД `perf112`, название API и отсутствие подготовленных пользователей.
  Повторный запуск на уже наполненной БД отказывается продолжать. Скрипт ничего не удаляет.
  Частично прерванную подготовку также повторяют на свежем тестовом томе.
- Учебные данные намеренно синтетические: общий класс, 100 разных учеников,
  два занятия по 20 карточек (4000 назначений), 112 и ДДС `crews-v2`, профиль с бригадой.
  По умолчанию карточки ДДС приходят раз в минуту; `--dds-interval 2` задаёт интенсивный
  стрессовый поток из первичного отчёта. Это параметр нагрузки, а не учебный норматив.
  Лимит занятия — два часа. Полный справочник и объём истории production проверяются отдельно.

## Подготовка

Команды выполняются из `112-backend`, каждая — одной строкой. Нужен Docker Compose.
Python на хосте нужен только для необязательного сборщика метрик.

```sh
docker compose -f performance/compose.yaml up -d --build api
docker compose -f performance/compose.yaml build load
docker compose -f performance/compose.yaml run --rm seed
```

API: `http://localhost:18000`, PostgreSQL: `localhost:15438`. Порты привязаны к localhost.
Манифест `performance/artifacts/manifest.json` содержит **тестовые** пароли, имеет права
0600 и исключён из Git. База/том/сеть относятся только к проекту `system112-performance`.
Для другого размера данных на **свежей** БД вместо последней команды:

```sh
docker compose -f performance/compose.yaml run --rm seed python -m performance.seed --users 200 --cards 50
```

Чтобы воспроизвести интенсивный профиль из `RESULTS.md`, при подготовке свежей БД:

```sh
docker compose -f performance/compose.yaml run --rm seed python -m performance.seed --users 100 --cards 20 --dds-interval 2
```

## Сценарии из ТЗ

| Требование / процесс | Проверка | Что результат означает |
|---|---|---|
| 100 пользователей, отклик интерфейса ≤2 с | `StudentWorkflow`, 100 виртуальных учеников | HTTP-задержки отдельно по маршрутам; не время отрисовки браузера |
| ≥20 одновременных карточек | Тот же сценарий с 20+ пользователями | Разные ученики, собственные попытки и ревизии, без искусственных конфликтов |
| 112 | Вход → журнал → открытие → ЕКП → черновик → подбор служб → аудит → отправка | Проверяются сохранённый текст, служба-получатель, завершение |
| ДДС / QA4 | Асинхронное поступление → открытие → назначена → принята → выезд → прибытие → работы → завершена → отправка | Обновления ревизий, реальные статусы; служебная история и оценка пишутся backend |
| Присутствие / возвращение | Heartbeat 15 с, выход и продолжение после первой карточки | API выхода/возвращения; здесь занятие с двухчасовым лимитом, пауза без лимита отдельно |
| Отчёт ≤30 с | `TeacherReports`, XLSX по группе | Валидный XLSX и фактическое время HTTP-выгрузки; запускать после накопления результатов |
| ≥100 операций записи/с | `capacity --mode writes --rates 50 100 150` | Успешно сохранённые черновики/с; не путать с количеством SQL-транзакций |
| Авторизация | Отдельный `LoginBurst` | Argon2, создание и отзыв сессии; не смешивать с чтениями при поиске их предела |
| 1000+ RPS | `capacity --mode reads` | Смесь кабинета, занятий, профиля и счётчика сообщений, без health-check в измерениях |
| Обрыв сети до 30 с | Отдельный browser/network test | Здесь **не проверяется** восстановление локального черновика после обрыва |
| VoIP ≤150 мс | Отдельный SIP/RTP стенд | Здесь **не проверяются** звук, jitter, loss, задержка и одновременные разговоры |
| ИИ и горизонтальное масштабирование | Отдельный профиль со своими ресурсами | Здесь **не подтверждаются** задержки LLM/очереди и масштабирование нескольких API-узлов |

Критерий ТЗ «не более 2 секунд» жёстче p95. Изучайте также максимум и p99;
зелёный p95 не доказывает выполнение ТЗ. Время API — только часть времени интерфейса.
Locust возвращает код 1 при HTTP/смысловой ошибке, незавершённом покрытии обоих ролей
или превышении максимума 2 с (для отчёта — 30 с). Начальная проверка адреса стенда
в этот бюджет не входит.

## Запуск Locust

Быстрая проверка всех основных HTTP-цепочек (4 пользователя, 60 секунд):

```sh
docker compose -f performance/compose.yaml run --rm load -f performance/locustfile.py --host http://api:8000 --headless -u 4 -r 2 -t 60s --stop-timeout 15 --csv performance/artifacts/smoke --html performance/artifacts/smoke.html StudentWorkflow TeacherReports
```

100 учеников, плавное подключение по 5 в секунду, 90 секунд:

```sh
docker compose -f performance/compose.yaml run --rm load -f performance/locustfile.py --host http://api:8000 --headless -u 100 -r 5 -t 90s --stop-timeout 30 --csv performance/artifacts/students100 --html performance/artifacts/students100.html StudentWorkflow
```

Половина учеников работает как 112, половина как ДДС. Между шагами 1–3 секунды.
Каждый получает собственную учётную запись. Завершение обоих типов карточек обязательно:
если прогон слишком короток и ни одна карточка одного типа не завершилась, код выхода 1.
Закончились ученики/карточки — ошибка набора данных, а не незаметная замена записей чтениями.
Для повторяемого сравнения используйте свежие данные. Прогон `writes` оставляет черновики;
их не следует смешивать с последующим измерением полного сценария без сброса фикстуры.

Проверка отчётов после прохождения учеников, затем отдельный вход/выход:

```sh
docker compose -f performance/compose.yaml run --rm load -f performance/locustfile.py --host http://api:8000 --headless -u 2 -r 1 -t 60s --csv performance/artifacts/reports TeacherReports
docker compose -f performance/compose.yaml run --rm load -f performance/locustfile.py --host http://api:8000 --headless -u 20 -r 2 -t 60s --csv performance/artifacts/login LoginBurst
```

Интерактивный интерфейс на `http://localhost:18089`:

```sh
docker compose -f performance/compose.yaml run --rm --service-ports load
```

Обычный запуск — один процесс генератора. Для distributed Locust каждый worker должен
иметь собственные `PERF_SHARD` (от 0) и одинаковый `PERF_SHARDS`: учётные записи делятся
срезами, иначе разные процессы будут менять одну попытку. Не используйте `--processes`
без явного разделения данных. Locust поддерживает отдельную машину генератора;
доступ к API открывайте только в тестовой сети.

## Фиксированная частота запросов и предел мощности

Locust — закрытая модель: при замедлении ответов виртуальный пользователь делает меньше
запросов. Поэтому для проверки 1000+ RPS есть небольшой отдельный open-loop планировщик
на asyncio/HTTPX. Он не ждёт ответа перед планированием следующего запроса, ограничивает
число незавершённых запросов и явно считает пропущенные поступления.

```sh
docker compose -f performance/compose.yaml run --rm --entrypoint python load -m performance.capacity --rates 100 250 500 1000 1500 --seconds 60 --output performance/artifacts/reads.json
docker compose -f performance/compose.yaml run --rm --entrypoint python load -m performance.capacity --mode writes --rates 50 100 150 --seconds 60 --output performance/artifacts/writes.json
```

Чтения: 20% профиль, 30% кабинет, 30% занятия, 20% счётчик сообщений. Логины выполняются
при подготовке и не входят в RPS. Записи: новая версия черновика с изменённым текстом;
у одной учётной записи не бывает двух конкурентных сохранений. Нужны свободные карточки.
Успех подтверждается HTTP 200 и ростом ревизии, а не только отсутствием исключения.
В режиме записи отдельные heartbeat поддерживают присутствие; их ошибки сохраняются
в `presence_errors`, но не прибавляются к RPS сохранений. После ошибочной записи актор
не используется повторно (таймаут мог скрыть успешный commit), а последующие ступени
не запускаются. Для их сравнения восстановите свежий набор данных.

JSON содержит заданный RPS, отправленные/успешные запросы, ошибки, p50/p95/p99/max,
`generator_dropped` (планировщик опоздал), `capacity_dropped` (лимит незавершённых запросов
или все пишущие ученики заняты), задержку планировщика и результаты по каждому маршруту.
`successful_rps` включает время ожидания последних ответов, чтобы не завышать результат.
По умолчанию разрешено 2000 незавершённых запросов. Планировщик допускает до 50 мс
задержки отправки, которую **включает** в измеренную задержку ответа. Более старые
поступления считает пропущенными; бесконечного догоняющего потока нет. Это устраняет
искусственный предел, когда дискретность таймера больше интервала при 1000+ RPS.
Для сравнения версий запускайте обе с одной версией генератора. При высокой доле `generator_dropped`
перенесите генератор на отдельную машину или разделите нагрузку; это не предел backend.
Не складывайте процентили независимых генераторов арифметически.

Код выхода 1, если на любой ступени ошибки + пропуски >1% либо p95 >2 с.
Это **рабочий порог эксперимента**, не полная приёмка ТЗ. При поиске предела такой выход
ожидаем. После перегрузки последующие ступени могут испытывать остаточную очередь;
для точного порога повторите отдельные ступени на свежей БД, с прогревом и 3–5 повторами.
Сначала используйте 10-секундные ступени как smoke, затем 60–300 с для измерений.

## Ресурсы и PostgreSQL

В отдельном терминале до запуска нагрузки:

```sh
python3 performance/monitor.py --seconds 420 --output performance/artifacts/resources.jsonl
```

Сборщик записывает CPU/память API, БД и генератора, параметры Docker, блокировки,
счётчики БД и top-15 `pg_stat_statements` по суммарному времени (без текста запросов).
SQL-счётчики накопительные: сравнивайте разности между снимками. `xact_commit` не равен
числу бизнес-записей. `shared_blks_hit` не означает попадание HTTP-ответа в кэш.
На высокой нагрузке проверяйте также ошибки пула и timeouts в логах API:

```sh
docker compose -f performance/compose.yaml logs --since 10m api
docker compose -f performance/compose.yaml exec -T db psql -U perf -d perf112 -c "SELECT queryid, calls, mean_exec_time, total_exec_time FROM pg_stat_statements ORDER BY total_exec_time DESC LIMIT 15;"
```

Сохраняйте Git SHA, версии образов, размер данных, настройки, JSONL ресурсов, CSV/HTML
Locust и JSON capacity. Генератор на том же Docker-хосте конкурирует за ресурсы с системой:
полученное число нельзя считать характеристикой будущего production-сервера.

## Остановка и повторная подготовка

Остановить только тестовый стенд, сохранив данные:

```sh
docker compose -f performance/compose.yaml down
```

**Удалить только нагрузочную БД** для следующего чистого прогона (рабочий Compose не затрагивается):

```sh
docker compose -f performance/compose.yaml down -v
```

Затем снова выполните подготовку. Старые CSV/JSON остаются в `artifacts`; выбирайте новое
имя отчёта, если результаты нужно сохранить. Пароли/токены не прикладывайте к отчётам.
Для длительных пользовательских прогонов увеличьте `--cards` при подготовке:
например, 50 карточек на роль для трёх минут; 100 для более длинной проверки.

Источники: [Locust — FastHttpUser и API](https://docs.locust.io/en/stable/api.html),
[стоимость генератора и несколько процессов](https://docs.locust.io/en/stable/increase-performance.html).

Результаты оптимизаций и повторных прогонов: [OPTIMIZATION_RESULTS.md](OPTIMIZATION_RESULTS.md).

## Перекрёстная проверка предела быстрым клиентом

Если HTTPX под перегрузкой сам загружает ядро и пропускает отправки, используйте
Locust FastHttpUser с той же смесью чтений, без пауз. Пример для 100 читателей:

```sh
docker compose -f performance/compose.yaml run --rm --no-deps -e PERF_SUMMARY=performance/artifacts/saturation.json load -f performance/locustfile.py --host http://api:8000 --headless -u 100 -r 20 -t 65s --reset-stats --stop-timeout 15 --csv performance/artifacts/saturation ReadCapacity
```

Это достигнутая пропускная способность в **закрытой** модели. Она не доказывает,
что сервер выдержит такой же независимо поступающий поток или столько же операций записи.
`--reset-stats` убирает стартовые входы после подключения всех пользователей;
для длительного steady-state увеличьте время. Сравните 20 и 100 читателей: рост очереди
без роста RPS указывает на насыщение. Смотрите CPU генератора, API и БД отдельно.
