# Поток карточек ДДС (QA3)

> Расписание сохраняет описанную здесь модель. Раздел о первой реакции относится к QA3: в новых упражнениях он заменён двумя нормативами и процессом [QA4](QA4_WORKFLOW.md). Паузы и лимит занятия описаны в [правилах времени](LESSON_TIMING.md).

Для новых занятий ДДС карточки поступают по серверному расписанию независимо
от завершения предыдущих. Оператор 112 сохраняет последовательную выдачу.
Уже начатые/назначенные до миграции занятия сохраняют прежний процесс и результаты;
для потока назначьте новое занятие. Новые занятия на существующих сценариях тоже
используют поток: миграция задаёт их карточкам смещения 0, 60, 120… секунд.

## Расписание и запуск

`ScenarioCreate.arrival_offsets_seconds` — целые неотрицательные смещения
от личного старта, по одному на `card_ids`, первое 0, остальные не убывают.
Нулевой интервал разрешает одновременное поступление. Последнее поступление должно
быть раньше `duration_minutes * 60`. По умолчанию ДДС — интервал 60 секунд,
оператор 112 — нули (без временной выдачи). Это настройка тренажёра, не норматив
заказчика. Лимита трёх ожидающих карточек нет.

Frontend показывает интервалы между поступлениями и рассчитанные смещения.
Порядок карточек можно менять, интервалы относятся к строкам расписания.
Версия сценария и назначения фиксируют расписание; последующее редактирование
не сдвигает действующие занятия.

`POST /student/lessons/{id}/start` явно запускает личное исполнение ДДС
(`LessonExecution`). Повторный запрос не сбрасывает часы. Начало доступности
занятия не запускает поток без ученика. Для старта до общей даты окончания
должно оставаться достаточно времени для поступления последней карточки.
Первый вызов старта первой карточки через API также может запустить исполнение.

Поля назначения: `scheduled_at` (план), `released_at` (доставка сервером).
В момент доставки создаются попытка и подготовленная карточка. Открытие
фиксируется отдельно (`first_opened_at`), не создаёт её заново и не сбрасывает время.
Пока карточка не поступила, в ученическом ответе нет её данных и названия ситуации.
Переход к будущей карточке даёт 409, чужая работа — 404.

Выдача выполняется вместе с серверной проверкой сроков под блокировкой занятия;
повторная обработка не создаёт дубликаты. Цикл работает раз в 5 секунд, независимо
от браузера и очереди LLM. Журнал обновляется TanStack Query раз в 5 секунд.
Норматив отсчитывается от фактической серверной доставки, не от запланированного
времени при задержке серверного процесса. Закрытие вкладки не останавливает выдачу.

## Реакция и завершение в исторической методике QA3

Рабочее учебное определение: первая успешная ручная запись статуса бригады,
включая её ручное назначение со статусом «Добавлена/Назначена». Просто открытие
карточки, отказанный запрос, автоматическое предзаполнение или подготовка бригад
реакцией не считаются. `Attempt.first_response_at` записывается один раз; повтор
идемпотентной команды и последующие статусы не меняют его.

Норматив берётся из снимка `norm_seconds`, по умолчанию 30 секунд. В журнале,
карточке и результатах показаны время первой реакции/отсутствие реакции и
соблюдение норматива. Это не утверждение о профессиональном регламенте:
конкретный вес штрафа не согласован, поэтому признак в проверке имеет `scored=false`.
Норматив не закрывает карточку. Общий срок и личный лимит всего занятия остаются условиями прекращения. В занятии без лимита выход приостанавливает поступление новых карточек и отсчёт реакции; после возвращения расписание сдвигается на время паузы. См. [LESSON_TIMING.md](LESSON_TIMING.md).
При общем окончании непройденное учитывается как 0 по существующей политике.

Статусы и время обновления службы не изменяются от действий с бригадой.
ДДС не проверяет грамматику и правильность заполнения исходной карточки 112.

## Аудит, помощь и телефон

Сохраняются `dds.card_received`, `dds.card_opened` с предыдущей карточкой,
`dds.crew_changed`, звонки и завершение. Подсказки по бездействию учитывают
выбранную карточку и недавние действия в других карточках того же занятия.
Анализ ИИ сохраняет ограниченную хронологию соседних карточек; в промпт передаётся
компактная сводка количества карточек/типов действий. Их ответы не смешиваются.
Переход на другую карточку не считается бездействием или ошибкой. Прокторинг
по-прежнему хранится отдельно. Длительность завершённых попыток считается
объединением интервалов, без двойного счёта пересечений; это не активное время ввода.

SIP-соединение frontend живёт в провайдере рабочего места, поэтому открытие другой
карточки/закрытие диалога не уничтожает гарнитуру. Звонок сохраняет свой attempt_id.
API состояния возвращает активный звонок рабочего места даже при просмотре другой
карточки; отмена направляется к его исходной попытке. Во время звонка смена
привязки телефона запрещена сервером. Один аппарат — один активный разговор.

По прямому указанию пользователя звонок ДДС заявителю исключён: контакт `caller`
скрывается из доступных реплик ДДС и запрещён в общем пути создания звонка,
включая адаптер внешней АТС. Исходная учебная голосовая подача для оператора 112
сохранена. Только учебные контакты, никаких внешних экстренных звонков.

## Применение и проверка

Миграция `0023_dds_stream`: расписание карточек, личное исполнение, план/доставка
назначений, первое открытие/реакция. Данные и старые результаты не удаляются.

Из backend: `docker compose up -d --build --wait api worker frontend`.
Compose применяет миграцию зависимым сервисом `migrate`. В demo seed готовое
оценённое и активное занятия ДДС имеют два одновременных поступления; четыре
не начатых учебных формата ДДС используют интервал 60 секунд.

Регрессии: `tests/test_dds_delivery.py`, seed, прежние workflows/телефония;
frontend `e2e/dds-stream.spec.ts`, скриншоты `docs/screenshots/dds-stream/`.
Внешние звонки, реальные ключи и новый прогон модели для этой задачи не нужны.
