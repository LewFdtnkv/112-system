# ЕКП, профили служб и упражнение ДДС

## Права и основание

В финальном ТЗ `ТЗ_ДГОЧСиПБ_финал_01092026ГСИ.docx`, в описании ролей
«Администратор» и «Преподаватель», администратору отнесены конфигурация и общие
настройки, преподавателю — подготовка и утверждение учебного содержания.
Прямого назначения редактора ЕКП там нет. Принятое **проектное распределение**:
администратор импортирует, редактирует и публикует общие ЕКП и профили служб;
преподаватель выбирает опубликованные версии, готовит карточки, сообщения,
эталоны действий и запускает занятия. Администратор не получает право менять оценки.

В интерфейсе: **Службы и классификаторы** → загрузка JSON / название версии /
профили служб. Сначала опубликовать ЕКП и профиль, затем создавать сценарий ДДС.
Учебная роль ДДС не меняет системную роль аккаунта ученика.

## Переносимый JSON

`POST /api/v1/admin/classifiers/import` принимает содержимое UTF-8 JSON-файла
(также UTF-8 BOM), не multipart. Максимум 8 МиБ, 2 000 правил, 1000 служб,
30 признаков и 100 маршрутов на правило. UI загружает выбранный файл;
`GET /admin/classifiers/{id}/export` возвращает attachment JSON, который можно
перенести в другую БД. Образец скачивается кнопкой «Скачать пример JSON».

```json
{
  "format": "system112-ekp-v1",
  "label": "Учебный ЕКП, версия 1",
  "services": [
    {"code": "training_fire", "name": "Учебная пожарная служба"},
    {"code": "training_med", "name": "Учебная скорая"}
  ],
  "entries": [{
    "code": "TRAIN.001", "section": "Учебные пожары", "name": "Пожар в доме",
    "response_scenario": "Искусственный учебный пример",
    "features": [{"key": "victims", "label": "Есть пострадавшие"}],
    "routes": [
      {"service_code": "training_fire", "is_main": true, "when": {}},
      {"service_code": "training_med", "is_main": false, "when": {"victims": true}}
    ]
  }]
}
```

Службы связаны по стабильным кодам, UUID рабочей БД не входят в файл. Импорт
переиспользует действующую службу с совпадающими кодом и названием; конфликт
названия/активности отклоняется. Новые службы и черновик создаются атомарно.
Дубликат названия версии не перезаписывает существующий справочник.

Признаки поддерживают `type: "boolean" | "choice" | "array" | "text"`, `required` и `options`.
По умолчанию тип boolean, required=true: прежние JSON остаются совместимыми.
Boolean принимает только true/false; choice — одну строку из options; array —
уникальный список строк (до 30). При заданных options элементы списка ограничены
этими вариантами, без options разрешён свободный список. Каждый вариант до 200
символов. В интерфейсе обязательные признаки помечены звёздочкой, остальные —
«необязательно», ответ можно очистить. Незавершённый черновик сохраняется;
при окончательном сохранении обязательные ответы нужны и при ручном выборе служб.

`when` означает **И** условий, `{}` — безусловный получатель. Boolean/choice
сравниваются точно, массив означает наличие **всех** указанных значений в ответе.
Неуказанный необязательный признак не соответствует false. Условие массива не
может быть пустым. Условий со скрытыми ключами и повторяющихся служб нет;
главная служба максимум одна, для обычного типа нужен безусловный маршрут.
Это подготовленный формат, **не автоматическая интерпретация всех условий XLSX**.

```json
"features": [
  {"key": "victims", "label": "Пострадавшие", "type": "boolean", "required": true},
  {"key": "place", "label": "Где", "type": "choice", "options": ["Дом", "Улица"]},
  {"key": "signs", "label": "Признаки", "type": "array", "required": false,
   "options": ["Дым", "Пламя"]}
]
```

Автопроверка сравнивает выбранные варианты с эталоном; порядок массива не влияет
на балл, дополнительные/пропущенные значения дают расхождение. Не заданные в
эталоне необязательные ответы не добавляют критерии. Свободный список строк
также сравнивается как набор значений; для смысловой оценки текста требуется
преподаватель или последующее подключение ИИ.

Преподаватель видит признаки при подготовке эталонной карточки, ученик — при выборе
типа происшествия. Получатели вычисляются на сервере; UI предварительно показывает
их по ответам без сохранения черновика. Признаки входят в формальную проверку типа
происшествия. Свободное смысловое содержание остаётся отдельным предметом проверки.

## Точечные правки и версии

- `GET /admin/classifiers/{id}/entries?q=&offset=&limit=` — компактная страница правил.
- `GET /admin/classifiers/{id}/entries/{entry_id}` — детали одного правила и revision.
- `PUT` по тому же пути: `{ "expected_revision": 1, "entry": { ... } }`.
- `POST /admin/classifiers/{id}/publish` — проверка и публикация.
- `POST /admin/classifiers/{id}/versions` с `{ "label": "Новое название" }` — копия
  в новый черновик для исправлений опубликованной версии.

Редактор позволяет менять код/название/раздел, описание реагирования, признаки,
главную службу и условия получателей. Новые массовые правила добавляются файлом.
Опубликованный справочник неизменяем. Редактирование черновика и публикация
сериализуются блокировкой версии; устаревший revision получает 409. Исходный JSON и
его SHA-256 сохраняются в import_report/source и source_sha256; hash описывает
**первоначальный импорт**, а не текущую редакцию после правок. Экспорт содержит
текущие правила. Версии ЕКП и снимки карточек существующих уроков сохраняются.
Старый POST `/admin/classifiers` с UUID остаётся для совместимости.

## Профили служб

`/admin/service-profiles`: POST создать, GET список с поиском/пагинацией;
`/{id}` GET/PUT; `/{id}/publish` POST. Обновление требует expected_revision.
Профиль содержит службу, название, ответственность, инструкцию, территории,
объекты с отдельным адресом и привязкой к территории, учебные контакты.
Код территории объекта должен существовать в том же профиле. Контакт указывает
действующую службу и локальный `endpoint_key`; это конфигурация учебного адресата,
не подключение реального звонка. Контакты могут относиться к разным службам.

Опубликованный профиль сохраняется. Правка через форму создаёт очередную черновую
версию этой службы. У преподавателя выборка `/service-profiles` содержит только
опубликованные профили. В попытке замораживаются выбранный профиль и его справочники.

## Выполнение ДДС

Новый сценарий `role=dds` требует опубликованный `service_profile_id` и `dds_policy`.
Каждая исходная карточка должна быть адресована службе профиля. `dds_policy.steps`
задаёт 1–7 сообщений и ожидаемых действий, например:

```json
{"steps": [
  {"status": "accepted", "message": "Карточка относится к ответственности вашей службы."},
  {"status": "completed", "message": "Наряд УЧ-42 сообщил: работы завершены.", "crew_number": "УЧ-42"}
]}
```

Последний этап определяет цель конкретного упражнения. Это не универсальное
утверждение, что каждое занятие обязано доходить до завершения работ. Порядок этапов
должен соответствовать допустимым переходам; номер наряда для оценки обязательно
присутствует в сообщении ученику. Старый сценарий ДДС без этапов нужно открыть и
сохранить новой версией: ранее опубликованные сценарии не изменяются миграцией.

Старт создаёт подготовленную общую карточку и отдельные ServiceResponse адресатов.
Статус `received` не равен `accepted`. Направление карточки ученику происходит при
старте попытки, фиксируется sent_at; от него показывается время первичного решения.
30 секунд — ориентир памятки, автоматический штраф по нему не введён.

`POST /student/attempts/{id}/dds/actions` принимает request_id, revision ответа службы,
information_event_id, status, crew_number, comment. Команда разрешена владельцу
попытки и меняет только свою службу. Вызов повторно с тем же request_id и содержимым
не дублирует событие; изменённое содержимое или устаревшая ревизия — 409. После действия
открывается следующее сообщение. Повторное применение уже обработанного сообщения
блокируется. Ответы следующих этапов не выдаются ученику заранее.

Получена → Принята / Не принята; после принятия доступны последующие состояния
(выезд, прибытие, проведение работ, завершение либо отказ). Возврат назад исключён;
промежуточные статусы не навязываются всем сценариям. Ошибочное допустимое решение
сохраняется и учитывается в оценке. «Не принята», «Отказ» и «Завершены» различаются.

`POST /student/attempts/{id}/dds/submit` с revision завершает попытку после
предусмотренного количества решений или терминального ответа. Завершение своей
службы **не завершает другие службы**; общая карточка становится completed только
когда все её ServiceResponse завершены. Готовую карточку ДДС нельзя переписать через
ручки оператора 112. Следующее задание открывается последовательно.

## Оценка и аудит

`dds-steps-v1`: 80% — соответствие последовательности статусов сообщениям, 20% —
заданные номера нарядов. Если номера не проверяются, балл нормируется по статусам.
Пропущенные/ошибочные действия снижают балл, правильные дают 100/100. Это учебная
базовая политика, не утверждённый норматив профессионального экзамена. Смысл
комментариев не оценивается буквальным сравнением и не влияет на этот автоматический
балл. Преподаватель видит сводку, сообщения, историю и может пересмотреть итог.

Сохраняются исходные сообщения, команды, отклонённые запросы, статусы, номера,
комментарии, server timestamps и ссылки CriterionEvidence. Будущий ИИ получает
замороженные dds_policy, профиль, карточку и историю в контексте оценки; контракт
допускает смысловую проверку `dds.comment`. Сам ИИ и SIP здесь не подключены.

Миграция `0009_catalog_revision` добавляет revision к справочникам/профилям,
не очищает данные. Проверки — `tests/test_catalog_dds.py`, полный HTTP seed и
frontend `e2e/catalog-dds-real.spec.ts`, включая скачивание/чтение JSON и снимки АРМ.

## Карточка оператора 112: подписи, популярные типы и службы

Миграции `0011_classifier_presentation` и `0012_manual_card_recipients`.
У записи ЕКП есть `display_name` (до 100 символов; иначе `name`), `is_popular`,
`popular_order` (меньшее число раньше) и `notification_required` (по умолчанию true).
Они доступны в JSON, редакторе правила, экспорте и копировании версии.
Редактировать опубликованный ЕКП нельзя: создать черновик новой версии, проверить,
опубликовать и выбрать его при подготовке новых карточек/сценариев. Миграция только
инициализирует подписи и четыре популярные кнопки известного seed v2; его маршруты,
коды и эталоны не переписываются. Полный набор быстрых кнопок есть в seed v3.

`GET /student/attempts/{id}/classifier-entries?popular=true` возвращает максимум 11
популярных записей закреплённого ЕКП. Поиск `q` начинается от двух непробельных
символов, пустая/короткая строка возвращает пустой список. LIKE-метасимволы
экранируются. Поиск не подменяется показом первой страницы ЕКП.

**Где задаются поля.** Администратор → «Службы и ЕКП» → версия → правило →
«Типовые признаки»: ключ, подпись, добавление/удаление. В JSON это `entries[].features`;
в БД — `classifier_entries.conditions` с format `typed-features-v1` (старый `boolean-features-v1` также читается). Поддержаны boolean, выбор одной строки и список строк, обязательность и варианты;
условия маршрутов находятся в `routes[].when` (AND). Общие поля
карточки (адрес, телефон, заявитель и т. п.) задаются моделью и компонентами формы,
а не произвольной схемой ЕКП; универсальный конструктор дополнительных форм не входит в этот формат.

**Службы — рекомендации.** По последнему прямому указанию пользователя оператор 112
может вручную добавлять/удалять службы через «+» и возвращать рекомендации ЕКП.
Это уточнение разрешает прежнее расхождение источников о праве удаления служб.
`GET /student/attempts/{id}/services` — доступные активные учебные службы с поиском
и пагинацией. Черновик принимает `recipient_service_ids`: null — следовать ЕКП,
список UUID — ручной выбор, [] — сознательно не оповещать никого. Список хранится
отдельно от типовых признаков в `incident_cards.recipient_service_ids` (JSONB),
проверяется на уникальность/активность при сохранении и повторно перед отправкой.
Ручной выбор сохраняется при изменении признаков/типа и перезагрузке. Имена берутся
с сервера; редактор показывает выбранные службы, а не скрытый эталон.

Тип с `notification_required=false` не содержит маршрутов и не требует адреса;
описание обращения остаётся обязательным. При пустом итоговом списке карточка
получает `registered`, попытка завершается, `notification_completed_at` остаётся
NULL, ServiceResponse не создаются. При ручном добавлении службы оповещение
выполняется по фактическому списку даже для служебного типа. Обычный тип без
настроенных маршрутов нельзя опубликовать, но ученик вправе вручную убрать
рекомендованные службы: его решение будет оценено, а не скрыто исправлено.

`card.services_changed` хранит предыдущее/новое решение и режим; регистрация без
оповещения — отдельное `card.registered_without_notification`. Учебный аудит
отделён от прокторинга. Оценка сравнивает фактические оповещения с эталоном;
для служебного эталона проверяется регистрация без оповещения. Ручной пересмотр
преподавателем доступен. Рекомендательные маршруты не являются запретом на
профессиональное решение; эталоны и текущие веса остаются учебными.

Для редких исключений преподаватель включает «Задать службы эталона вручную»
в форме создания карточки. `CardCreate.use_recommended_recipients=false` разрешает
эталонный список активных служб, отличающийся от ЕКП, включая пустой. При значении
true (по умолчанию) сохраняется проверка совпадения с рекомендациями. Признаки
эталона должны быть заполнены в обоих режимах; список фиксируется в снимке сценария.
Сведения, объясняющие исключение, преподаватель указывает в условии для ученика.

## Наименования служб и точка происшествия

`services.name` — полное официальное наименование (до 255 символов),
`services.short_name` — короткая подпись (до 100, nullable для старых данных).
Оба поля доступны в JSON services, API справочников и поиске. В выборе служб
показаны оба названия; в нижней панели карточки — короткое, если заполнено.
Администратор создаёт или редактирует названия по нажатию на строку службы;
`PATCH /admin/services/{id}` принимает name и short_name. Код не изменяется.
Уже направленная карточка сохраняет снимки обоих названий в ServiceResponse.
Импорт не перезаписывает отличающееся название существующей службы; её нужно
исправить явно. Пустую короткую подпись импорт может дополнить.

Точка карты хранится в `data.additional_fields.location`:
`{"latitude": 55.7558, "longitude": 37.6173}`, null означает отсутствие точки.
Сервер проверяет диапазоны ±90/±180 и числовые значения; текстовый адрес остаётся
независимым. Подтверждённое изменение координат попадает в учебный аудит
`ui.field_changed` и снимок `card.draft_saved`, а не в прокторинг. Координаты сейчас
не добавляют штраф/балл: допустимая погрешность географического эталона не задана.
Подключение Яндекс.Карт описано в frontend `docs/MAPS.md`.

## Зависимые поля и исходный справочник

`visible_when` задаёт группы условий видимости (ИЛИ между группами, И внутри),
ссылки только на предшествующие поля. JSONB уже поддерживает эти данные.
Frontend очищает скрывшиеся ответы, backend отклоняет скрытые значения.
Подробнее и происхождение данных: [DEMO.md](DEMO.md).
