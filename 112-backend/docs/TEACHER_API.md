# Подготовка и запуск урока

Все пути ниже имеют префикс `/api/v1`. Защищённые запросы передают
`Authorization: Bearer <access_token>`. Полные схемы доступны в `/docs`.
UUID в примерах — обозначения; подставлять идентификаторы из ответов API.

## 1. Администратор создаёт аккаунты

После смены собственного стартового пароля администратор вызывает `POST /users`:

```json
{
  "username": "teacher1",
  "initial_password": "temporary-password-112",
  "first_name": "Иван",
  "last_name": "Иванов",
  "role": "teacher"
}
```

Для ученика `role: student` (значение по умолчанию); роли взаимоисключающие. Допустимы `middle_name`, `email`.
Стартовый пароль — 12–128 символов, не только пробелы. Логин нормализуется в нижний регистр;
дубликат возвращает `409`. Пароль хранится только как хеш, в ответ не возвращается.
`is_active=true` и `must_change_password=true` устанавливаются сервером.

Новый пользователь входит через `POST /auth/login`. Пока он не вызовет
`POST /auth/change-password`, прикладные ручки возвращают `403 password_change_required`.
Изменение пароля выдаёт новую пару токенов и отзывает прежние сессии.

## 2. Преподаватель создаёт группу

`POST /groups` с `{"name":"Группа 1"}` создаёт `training_groups` с владельцем из токена.
Преподаватель выбирает учеников через `GET /users`, затем для каждого вызывает
`PUT /groups/{group_id}/students/{student_id}` без тела: создаётся `group_memberships`.
Повторное добавление возвращает ту же запись. Можно добавить ученика, который ещё не сменил
пароль; начать работу до смены он не сможет. Администраторы, преподаватели и неактивные
аккаунты участниками учебной группы через этот API не назначаются (`409`).

## 3. Подготовленные справочники и ручная карточка

До создания карточек в БД должны быть проверенная версия ЕКП со статусом `published`, её
`classifier_entries`, `classifier_routes` и соответствующие активные `services`.
Выбор версии делается явно; более поздний XLSX автоматически не подменяет предыдущий.
Пустая новая БД этих данных не содержит. Администратор может создать службы через
`POST /admin/services` (`code`, `name`), затем черновик справочника через
`POST /admin/classifiers`: `label`, `source_filename`, `entries` со свойствами
`code`, `section`, `name`, `service_ids`. Это JSON-контракт простых безусловных маршрутов,
не импорт исходных XLSX. Исходный JSON и его SHA-256 сохраняются в БД.
`POST /admin/classifiers/{id}/publish` проверяет маршруты и публикует версию от имени
администратора. Повторная публикация безопасна. Редактирования опубликованных версий нет.

Получить идентификаторы и условия можно через `GET /classifiers`,
`GET /classifiers/{version_id}/entries`,
`GET /classifiers/{version_id}/entries/{entry_id}/routes` и `GET /services`.

`POST /cards`:

```json
{
  "title": "Дерево во дворе",
  "classifier_version_id": "<UUID опубликованной версии ЕКП>",
  "classifier_entry_id": "<UUID кода этой версии>",
  "caller_message": "Во дворе на Учебной улице, 1 упало дерево. Пострадавших нет.",
  "instructions": "Заполните карточку по сообщению заявителя",
  "data": {
    "caller_name": "Учебный заявитель",
    "address_text": "Учебная улица, 1",
    "description": "Упало дерево, пострадавших нет",
    "features": {"has_victims": false}
  },
  "recipient_service_ids": ["<UUID учебной службы из маршрутов кода>"]
}
```

Создаются `card_templates` и `card_template_recipients`. Это библиотечный материал;
`incident_cards` появится только при будущей реализации ученической попытки.
Обязательны непустые `title`, `data.address_text`, `data.description`, код и версия ЕКП,
а также список получателей без повторений (может быть пустым для регистрации без оповещения).
В `data` дополнительно допустимы `caller_phone`, `caller_details`, `address_details`,
`victim_details`, `features`, `additional_fields`. Произвольные дополнительные поля
передаются внутри `additional_fields`, а не на верхнем уровне.

При `use_recommended_recipients=true` (по умолчанию) получатели должны соответствовать
ЕКП. Для исключения преподаватель задаёт false и произвольный список активных служб,
включая пустой. Boolean/choice/array признаки с required=true заполняются явно;
необязательные можно пропустить. Неизвестные ключи отклоняются. Обычный тип должен
иметь подготовленные маршруты; тип с notification_required=false не имеет маршрутов.
Подробные типы и форматы — [CATALOG_AND_DDS.md](CATALOG_AND_DDS.md).

Для оператора 112 `caller_message` — условие, `data` — скрытый образец заполнения;
для ДДС `data` — готовые исходные сведения. Ответы `/cards` и `/scenarios` предназначены
только преподавателю: передавать их ученику целиком нельзя.

## 4. Преподаватель собирает сценарий

`POST /scenarios`:

```json
{
  "title": "Три последовательные карточки",
  "role": "operator_112",
  "card_ids": ["<UUID карточки A>", "<UUID карточки B>", "<UUID карточки C>"],
  "instructions": "Обработайте карточки по очереди"
}
```

Для `role=dds` обязательны `dds_policy.steps` и `service_profile_id` из `GET /service-profiles`:
профиль должен быть опубликован, его служба активна и присутствовать в получателях
каждой карточки. Для `operator_112` у каждой карточки обязателен `caller_message`.
Карточек от 1 до 100; одна карточка может повторяться на разных позициях.
Все карточки принадлежат преподавателю и используют одну опубликованную версию ЕКП.

Создаются `scenarios`, `scenario_versions` (версия 1) и `scenario_cards` с `position=1..X`.
В `scenario_cards.snapshot` копируются сведения, текст заявителя, инструкции,
классификация и получатели: дальнейшее изменение шаблона не меняет снимок.
Этот ручной запрос считается подтверждением подготовленного состава преподавателем:
версия получает `published`, `approved_by_id` и `approved_at`.
API редактирования опубликованных версий отсутствует. Прямой SQL не защищён от UPDATE
триггерами; будущие редакторы должны выпускать новые версии.

Ответ содержит `id` **версии**, используемый при запуске, и отдельный `scenario_id`.
`answer_keys.rubric` хранит версионированную `assessment_policy` с весами
формальных критериев оператора 112. Эталоны действий ДДС и сообщения задаются
в `dds_policy.steps`; контракт — [CATALOG_AND_DDS.md](CATALOG_AND_DDS.md). Предварительное сравнение полей использует снимок карточки,
см. [AUTOMATIC_CHECK.md](AUTOMATIC_CHECK.md).

## 5. Преподаватель запускает урок группы

`POST /lessons/start`:

```json
{
  "request_id": "<новый UUID запроса запуска>",
  "group_id": "<UUID своей группы>",
  "student_id": "<UUID ученика этой группы, необязательно>",
  "scenario_version_id": "<id из ответа POST /scenarios>",
  "title": "Практическое занятие",
  "learning": {"kind": "practice"},
  "time_limit_seconds": 180
}
```

`title` необязателен: по умолчанию используется название сценария.
`learning` задаёт вид занятия, цель, навыки и будущую помощь; по умолчанию практика
без помощи. Контракт и ограничения: [Основа учебных режимов](LEARNING_FOUNDATION.md).
Роль и профиль берутся из сценария. Лимит времени необязателен, от 1 до 86400 секунд;
это настройка **каждой карточки**, не общий норматив или лимит всего урока.
Указанные числа в примере не являются нормативами.

Если передан `student_id`, урок назначается только этому ученику своей группы;
без него — всем текущим ученикам группы. Чужой или отсутствующий в группе ученик — `404`.

За одну транзакцию создаются:

- `lessons`: статус `active`, серверное `started_at`, преподаватель, группа, выбранная версия,
  `start_request_id` и отпечаток параметров запроса;
- `assignments`: X назначений каждому текущему ученику группы, со ссылками на версию и
  конкретную `scenario_cards`, порядком `position=1..X` и выбранными настройками.

В ответе — `student_count` и `assignment_count`; при двух учениках и трёх карточках
это 2 и 6. Пустая группа, неактивный участник, участник с правами персонала, неопубликованные
сценарий/ЕКП/профиль или неактивный получатель дают `409`, без частично созданного урока.
Состав группы фиксируется назначениями; добавление ученика после запуска не меняет урок.

Первый запуск возвращает `201`. Повтор с тем же `request_id` и теми же параметрами
возвращает тот же урок и `200`, даже если состав группы впоследствии изменился.
Другие параметры под тем же `request_id` дают `409`; новый UUID создаёт новый урок.
Ключ изолирован по преподавателю, конкурентные запуски также защищены.

Посмотреть результат: `GET /lessons/{id}` и `GET /lessons/{id}/assignments`.
`attempts`, ученические карточки и таймеры выполнения при запуске преподавателем не создаются.
Ученический старт, последовательная работа оператора 112 и ручная оценка урока
реализованы в [STUDENT_WORKFLOW.md](STUDENT_WORKFLOW.md). ДДС, профили, импорт/экспорт
файлов ЕКП и точечный редактор — [CATALOG_AND_DDS.md](CATALOG_AND_DDS.md). ИИ и SIP пока не подключены.


## Автоматическая оценка

Создание/новая версия сценария принимает `assessment_policy`: `version: weighted-fields-v1`,
`weights: {classification: 25, notification: 25, address: 30, caller: 10, victims: 10}`.
Все веса целые, 1–100; при отсутствии используются эти значения. Ответ сценария
возвращает политику. Эталонные факты берутся из опубликованных снимков карточек.
См. [политику и пересмотр](ASSESSMENT_ARCHITECTURE.md).

## Метаданные эталонного решения для просмотра в АРМ

`CardRead` в `POST /cards` и `GET /cards/{card_id}` дополнительно возвращает:

- `classifier_entry`: выбранный тип происшествия с описанием признаков либо `null`;
- `recipients`: упорядоченный список `{service_id, name, short_name}`.

Существующий `recipient_service_ids` сохранён. Фронтенд получает тип, признаки
и полные/короткие названия служб вместе с карточкой, без цепочки запросов.
Эти ответы доступны преподавателю-владельцу; ученик получает 403,
другой преподаватель — 404. Ученический API не расширялся эталонными данными.
Для назначенного задания просмотр по-прежнему использует зафиксированный снимок
из `WorkReview`, а не изменяемое представление библиотечной карточки.
Миграция БД не требуется.

## Изменение неиспользованной карточки

По уточнению пользователя изменять можно только карточки, ещё не включённые
в сценарии. История редакций карточек не вводится.

`PUT /cards/{card_id}` принимает поля `CardCreate` и обязательный `revision >= 1`.
Права: только преподаватель-владелец. Сохраняются ID и дата создания; увеличивается
технический счётчик `revision`, обновляется `updated_at`. Данные, признаки,
принадлежность типа версии ЕКП и состав активных служб проверяются теми же правилами,
что при создании. Изменение полей и получателей атомарно.

- 403: ученик или администратор без учебных прав.
- 404: чужая или отсутствующая карточка.
- 409: устаревший revision либо карточка уже есть в любой сохранённой версии
  сценария, включая черновик и архивированную историю.
- 422: недопустимые данные или получатели.

`CardRead` содержит `can_edit`, `scenario_count`, `revision`, `updated_at`,
`classifier_label`. Счётчик сценариев считает разные сценарии, а не повторения
карточки или число редакций сценария. `GET /views/cards` добавляет компактные
`incident_name`, `address_text`, `recipients`, `scenario_count`, `classifier_label`;
тело решения в список не передаётся. Получатели всей страницы загружаются пакетом.

Редактирование и сборка сценария блокируют строки карточек; сборка берёт блокировки
в порядке ID. Это не позволяет включить в сценарий половину обновлённых данных.
Миграция `0014_card_template_editing` добавляет только revision и updated_at;
для существующих карточек время изменения инициализируется временем создания.

## Учебные форматы v2

Запуск принимает `learning` с kind, objective, target_skills и
`assistance: {"max_level": "none|goal|explanation|solution", "on_request": true}`.
Время и способ показа подсказок больше не задаются преподавателем. Навыки доступны
только в `skill_practice`/`review`; остальные поля подготовлены и не оцениваются.
Новые занятия ДДС требуют целей бригад, статусы службы не используются.
Контракт и ограничения: [учебные режимы](LEARNING_FOUNDATION.md).
