# Начальные процессы BPMN

Источники: корневые `bpmn_proc (2).drawio`, `BPMN.md` и уточнения пользователя
20.09.2026. Диаграмма описывает функции и экраны, а не исполняемую BPMN-модель.

## Термины и совместимость

Карточка — одна ситуация. Сценарий — упорядоченный набор карточек. Задание —
назначенный сценарий с получателями и окном доступности. Существующие названия
таблиц/API сохранены: `lessons` хранит задание, `assignments` — карточки каждого
ученика. Переименование таблиц не требуется и сломало бы действующие интеграции.

`POST /lessons/start` принимает старые `group_id`/`student_id` или новые
`group_ids`/`student_ids`, а также `available_from`/`available_until` с часовым поясом.
Получатели проверяются в области преподавателя и дедуплицируются. Группы фиксируются
блокировками; состав назначений после запуска неизменяем. Повтор запроса с тем же
`request_id` идемпотентен. Для нескольких групп `group_id` задания пустой.

## Сроки и оценка

Будущий старт создаёт `planned`; до указанной даты начать карточку нельзя.
Фоновая задача API раз в 5 секунд проверяет задания; команды дополнительно проверяют
срок на сервере. Закрытая вкладка не останавливает время. Для нескольких процессов
используется блокировка задания с `SKIP LOCKED`.

Новые попытки фиксируют `deadline_policy=bpmn-v1`. Уже открытые до обновления попытки
не получают ранее неработавший лимит задним числом; их можно завершить прежним способом.
Эффективный срок новой карточки — минимум общего окончания и `started_at + time_limit_seconds`.
По сроку открытая попытка становится `interrupted` с `end_reason=deadline_expired`.
Оценивается последний сохранённый черновик; оповещение и действия ДДС не выполняются
автоматически. Лимит отдельной карточки открывает следующую; общий срок блокирует все.
Неначатые карточки остаются неначатыми, а не имитируются как действия ученика.

Если есть пропуски, итог — сумма процентов оценённых карточек, делённая на число всех
назначенных карточек. Неначатая карточка даёт 0. Оценка полностью пропущенного задания
равна 0. В `assessment_details.missed_cards` сохранено число пропусков. При полном
прохождении сохранён прежний расчёт по весам критериев. Ручной пересмотр преподавателя
создаёт новую ревизию и имеет приоритет. Таймеры и веса учебные, не профессиональные нормативы.

## Два независимых журнала

- `attempt_events` и `/observations`: учебные действия, команды, изменения полей,
  отказы и оценивание. Источник для подсказок и будущего ИИ-оценивания.
- `proctoring_events` и `/student/attempts/{id}/proctoring`: только `tab.visible`,
  `tab.hidden`, `window.focus`, `window.blur`. Отдельные таблица, схема, API и UI.
  Прокторинг не попадает в контекст оценивания и не уменьшает балл.

События браузера непроверенные. Потеря фокуса не доказывает списывание и не означает
обнаружение другой программы, отсутствия ученика или постороннего звука. Доступны
серверное время приёма и время браузера. Повторы идемпотентны; изменение содержимого
под тем же UUID отвергается. Лимит — 2000 событий на попытку, пакет до 20. Поздняя
отправка допускается 5 минут после окончания. Учитель видит только свои задания через
`/teaching/monitoring` и `/teaching/attempts/{id}/proctoring`.

| 90,96,105: комментарии | Объявление снимку текущих участников группы и личные сообщения; кабинет и рабочее место ученика, отметка чтения |

Создание учётных записей остаётся исключительно административной функцией.
Перевод/исключение ученика не удаляет прежние задания и полученные сообщения.
Использованный архивный сценарий не допускает новой публикации или назначения.

## Экспорт и фотографии

Экспорты требуют авторизации. XLSX записывает пользовательский текст как строковые
ячейки, без выполнения формул. Выгрузка ограничена 10000 строками; для отчётов можно
сузить область группой/учеником. Не смешивает прокторинг с учебным журналом.

Фото загружает администратор: PNG/JPEG до 2 МБ и 16 мегапикселей. Сервер декодирует,
уменьшает до 512×512, удаляет метаданные повторным кодированием JPEG. Бинарные данные
хранятся отдельно от списков пользователей. Читать может сам пользователь, администратор
или преподаватель ученика, доступного ему по группе/истории заданий.

## Системное сопровождение

HTTP-журнал содержит время, шаблон маршрута, метод, статус, длительность, request ID
и класс необработанной ошибки. Пароли, токены, заголовки, query string и тела запросов
не сохраняются. Ротация: текущий файл и 3 архива по 5 МБ; история до внедрения не создаётся.
`SYSTEM_LOG_DIRECTORY` задаёт путь (в образе `/home/appuser/logs`). Compose подключает volume `request_logs`, сохраняющий журнал между
пересозданиями контейнера. При отдельном запуске подключить volume к этому каталогу. При нескольких API-процессах
выделять каждому свой каталог/сборщик логов; общий RotatingFileHandler не предназначен
для конкурентной ротации несколькими процессами.

Согласно комментариям BPMN, настройки БД и резервное копирование исключены из вебки.
Параметры БД задаются переменными окружения при развёртывании. Резервные копии выполняет
системный администратор средствами PostgreSQL; перед внедрением проверяется восстановление.

Отдельные последующие этапы: генерация и рекомендации ИИ, SIP/VoIP, запись экрана/камеры.
Работа по локальному HTTP не требует `crypto.randomUUID`: frontend использует UUID v4
на основе `crypto.getRandomValues`, если более новый API недоступен.

## Проверка реализации

На отдельной PostgreSQL проверены 144 backend-теста, миграция с чистой БД и
`alembic check`. Frontend: lint, build, 62 Vitest; 11 браузерных сценариев
(10 в общем прогоне и отдельный повтор BPMN после исправления ответа API).
Новый сквозной сценарий проверяет сообщения, профиль, датированное задание,
автосохранение, отдельный прокторинг, окончание срока с пропуском и экспорт журнала.
Node и Playwright запускались в Docker. Скриншоты лично просмотрены и сохранены
в frontend `docs/screenshots/bpmn-*.png`; рабочая карточка сопоставлена с исходным DOCX.
