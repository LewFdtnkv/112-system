# Проверка живых сообщений заявителя — 25.09.2026

## Что изменилось

В v4 модель выбирала три номера готовых фраз. Теперь она действительно пишет
монолог или СМС. Эталон, признаки, адрес, имя и службы фиксирует сервер до очереди;
модель получает наблюдаемые факты, но не таблицу правильных ответов. Точные адрес и
имя подставляются через маркеры. Отдельный вызов модели проверяет сохранность фактов,
пропуски и новые обстоятельства. Есть одна попытка исправления. При отказе или
тайм-ауте публикуется явно подписанная заготовка, а не якобы успешный текст ИИ.

«Я женщина» удалено из заготовок и запрещено в модельном тексте. Пол и АОН остаются
отдельными сведениями для оператора. Неизвестные необязательные отрицательные
сведения больше не заставляют заявителя читать анкету. Если преподаватель явно
задал отсутствие пострадавших или отказа, эта информация должна остаться в условии.

В карточке преподавателя появилась отметка «Использовать как пример генерации».
Подбираются только собственные одобренные примеры того же типа ЕКП и канала,
совместимые по признакам, отметкам и числу пострадавших. Один такой пример дополняется
одним из 21 авторского образца. Это структурный RAG из PostgreSQL: для небольшого
типизированного корпуса отдельный embedding-поиск не требуется. Существующий
векторный RAG оценивания не менялся. Редактирование снимает одобрение; worker
повторно проверяет его перед публикацией. Начальные образцы синтетические.

## Методика и эксперименты

Это инженерная проверка небольшой специально выбранной выборки, не статистическая
оценка всех происшествий и не экспертиза оператора 112. Все приведённые ниже модельные
ответы получены настоящими запросами Ollama; учебные личности и адреса — тестовые.
Черновики, исходные факты, промпты, вердикты и время сохранены в JSON рядом с отчётом.

| Этап | Объём | Наблюдение |
| --- | ---: | --- |
| Простое перефразирование фактов | 5 | Часто почти дословный список; встречались АОН в речи заявителя и неестественные фразы |
| Те же случаи с общими примерами | 5 | В случае запаха газа модель скопировала пожар мусора из образца. Общий RAG без фильтров оказался опасным |
| Подробный критик с цитатой на каждый факт | 2 | Оба запуска превысили общий бюджет 300 с на исходном ограничении CPU; не засчитывались как успешная проверка смысла |
| Компактный критик, первый вариант | 3 | Пропущены придуманные отрицания «никто не зажат», «машины не горят»; медицинский текст отклонён |
| Короткие совместимые образцы | 4 | Смысл лучше, но оставались «в живую», «могу помочь» от лица оператора, неестественное склонение адреса |
| Одинаковые новые промпты, 4B против 8B | 2 + 2 | 8B убрала нелепую просьбу «связать это наблюдение» в ДТП; медицинский монолог у обеих моделей сухой |
| Развёрнутые образцы с условиями совместимости, 8B | 8 | Все прошли автоматическую проверку; при ручном чтении остались стилистические и смысловые нюансы |

Источники: [прототипы](prose-prototypes.json),
[долгий критик](prose-detailed-critic-timeouts.json),
[первая проверка](prose-first-review.json),
[короткие примеры](prose-minimal-examples.json),
[парный 4B](prose-role-4b.json), [парный 8B](prose-role-8b.json),
[восемь 8B](prose-matched-8b.json).

В прогоне 8B формальные 8/8 не означают 8 безупречных текстов: медицинский ответ
оставался перечислением; в газовом вызове возникло «у меня в квартире» вместо просто
помещения, а доступность места сузилась до «в подъезде свободно». Критик это пропустил.
Поэтому увеличение модели само по себе проблему не решает. Основная модель осталась
Qwen3 4B Instruct-2507 Q4_K_M; 8B Q4_K_M использовалась только для сравнения.

После этой серии исходные опорные фразы дополнительно сделаны разговорными:
«Сюда можно добраться», «Никто не пострадал», «От скорой никто не отказывался».
Итоговые восемь 4B используют уже эти фразы, поэтому их нельзя выдавать за строго
парное сравнение с восемью 8B. Контролируемое сравнение моделей — только две пары выше.

## Итоговая серия 4B

[Все восемь полных результатов](prose-matched-4b.json), без отбора удачных.
Все 8 первоначально получили `assisted`, все сохранили точные имя и адрес,
в речи не было «Я женщина». Это формальная приёмка, а не оценка качества прозы.

| Случай | Время, с | Ручное чтение |
| --- | ---: | --- |
| Короткое анонимное СМС о мусоре | 90.62 | Кратко и по делу; первое время включает загрузку |
| ДТП, два пострадавших | 52.51 | Наиболее естественный из сложных случаев, число и условия сохранены |
| Без сознания, дышит | 35.56 | Факты сохранены, но повтор «ещё дышит / дыхание есть» и неудачное «не в себе» |
| Запах газа у плиты | 54.11 | Связная речь; «у нас в доме» слегка уточняет отношение заявителя к месту |
| Описательный адрес, только имя | 72.85 | Ориентир точный, факты сохранены, но снова короткий список предложений |
| СМС с явно заданными ФИО и возрастом | 59.70 | Все заданные сведения сохранены, демографический блок делает СМС менее естественным |
| Пожар, вариант A | 78.78 | Неудачное окончание «Просьба о помощи». Критик его пропустил; добавлена отбраковка и выполнен повтор |
| Пожар, вариант B | 46.57 | Корректно, но почти исходный перечень фактов |

В этих восьми не обнаружено грубых подмен происшествия, адреса или числа людей.
При строгом прочтении минимум два смысловых нюанса требуют внимания: «не в себе»
можно понимать иначе, чем потеря сознания, а «у нас в доме» добавляет отношение
заявителя к месту. Это не основание заявлять «0% смысловых ошибок».
По субъективной оценке автора проверки пять из восьми текстов по-прежнему требуют
стилистической редакции: медицинский, описательный адрес, полное СМС и два пожарных.
Заметное улучшение есть у ДТП, но цель устойчиво живой речи достигнута лишь частично.

Пример из настоящего результата ДТП:

> Алло! Тут на дороге две машины столкнулись, это Москва, Лесная улица, д. 12.
> Двое пострадали, им помощь нужна. Подъехать можно. Нет, от скорой никто не
> отказывался, пришлите, пожалуйста. Меня зовут Анна Иванова.

Для сравнения, неизменные сведения АОН, пола, возраста и объекта в JSON остаются
отдельным операторским блоком; в цитате приведён только монолог.

## Проверка отбраковки

В [повторе пожарного случая](prose-fire-recheck.json) первая попытка снова дала
«Просьба о помощи». Новый фильтр её отклонил; вторая попытка написала «Помогите,
пожалуйста» и прошла проверку. Обе попытки сохранены. Это исправление конкретного
наблюдённого сбоя, не универсальный детектор неестественной речи.

Отдельно настоящему критику 4B поданы три намеренно испорченных текста и один верный:

| Текст | Ожидание | Результат |
| --- | --- | --- |
| Пожар мусора вместо запаха газа | Отклонить | Отклонён |
| «Не дышит» вместо «дышит» | Отклонить | Отклонён |
| Три пострадавших вместо двух | Отклонить | Отклонён |
| Правильное перефразирование газового вызова | Принять | Принят |

Все четыре решения совпали с ожиданиями, сетевых ошибок не было. Однако объяснения
критика не всегда аккуратны: он иногда исключает из covered и сохранённые факты,
а в unsupported перечисляет исходную фразу. Поэтому его текст не показывается
ученику и не используется как эталон. Четыре специально выбранных случая не позволяют
оценить процент ложных допусков или отказов на реальном потоке.
[Исходные ответы](prose-critic-calibration.json), повтор:
`python -m scripts.evaluate_generation_critic`.

## Настоящая задача с примером преподавателя

На отдельной мигрированной PostgreSQL создан тестовый преподаватель и вручную
подготовленный образец ДТП. Пример одобрен через команду API; зарегистрирована задача,
worker получил lease, выбрал пример из БД, вызвал реальную 4B и критика, сохранил
новую карточку. Статус `succeeded`, источник `assisted`, в аудите есть ID и редакция
преподавательского примера. Новая карточка автоматически не одобрена.

В этом случае «никто не зажат, машины не горят» — допустимые сведения: оба отрицания
явно заданы в параметрах. Они не были перенесены в случай, где эти признаки неизвестны.
[Полный вход и результат worker](prose-live-teacher-rag.json).
Это один синтетический интеграционный случай, не проверка на реальной методической
библиотеке преподавателей. Он подтверждает работу пути через БД/очередь/публикацию.

[Условия и решения в удобном для чтения виде](PROSE_V5_EXAMPLES.md).

## Проверки кода и интерфейса

Полный backend pytest: 397 тестов, включая права, ревизии, отзыв примера, несовместимые
состояния, публикацию, очередь и существующие процессы обучения. Новая миграция
согласована с моделями (`alembic check`). Дополнительный тест отбраковки фразы
«Просьба о помощи» прошёл в целевом наборе. Финальный обязательный pre-commit прошёл, включая полный pytest на отдельной
тестовой PostgreSQL.

Frontend: build, lint и FSD прошли. Все 146 уникальных Vitest прошли с повтором
тестов, превысивших тайм-аут при параллельной работе модели; первоначальный массовый
запуск не был полностью успешным. Playwright проверил одобрение, отзыв, использованную
карточку и конфликт редакции на API-фикстурах. Итоговые desktop/mobile снимки лично
просмотрены: `112-frontend/docs/screenshots/generation-prose`.

## Ограничения

- Критик — та же небольшая модель в отдельном запросе. Его согласие не доказывает
  отсутствие ошибок; узкие программные проверки ловят лишь известные классы сбоев.
- Реальное разнообразие сюжета всё ещё ограничено 37 подготовленными ситуациями;
  новая схема расширяет речь, порядок и связки, но не создаёт бесконечно новые события.
- Заданные факты всё равно должны быть доступны ученику. Задача — естественно
  сообщать их, а не скрывать необходимые ответы в неизвестных обстоятельствах.
- Пример преподавателя — опорный материал, не автоматическое дообучение модели.
  Всеобщая библиотека чужих карточек не включена. Точный поиск по типу ЕКП не переносит
  примеры между различными версиями записей справочника.
- Исторические карточки и назначенные занятия не переписываются. Для новой схемы
  нужно создать новый пакет; перед включением в сценарий преподаватель читает результат.

## Среда и воспроизводимость

Ollama 0.34.2, CPU в Docker Desktop. Последние сравнения — отдельный контейнер до
6 CPU, 4 GiB для 4B / примерно 6.5 GiB для 8B, контекст 4096, writer temperature 0.45,
critic 0, фиксированные seed, одна задача одновременно. Рабочий Compose оставлен
с прежними лимитами; эти времена нельзя обещать для его 2 CPU или другого сервера.
Первый запрос включает загрузку модели. Время и потребление не являются бенчмарком.

После сравнения моделей один технический запуск попал на остановленную Ollama:
восемь немедленных fallback за ~0.01 с. Он исключён из оценки качества, затем проведён
полный повтор на работающей модели. Причина — уменьшение тестового лимита памяти при
ещё загруженной 8B; это не отказ генерации 4B и не основание увеличивать память стенда.

Команда внутри backend-контейнера (пишет JSONL, не меняет БД):

```sh
python -m scripts.evaluate_generation --cases-file docs/generation-evaluation/prose-v5-cases.json
```

Для сравнения модели добавить `--model qwen3:8b-q4_K_M`. Исторические ответы сохранены;
повтор на другом железе или после обновления модели может отличаться.

## Контроль на обновлённом стенде

После обновления API/worker/frontend и миграции 0028 повторён случай ДТП на штатной
Ollama: 2 CPU, 4 GiB, та же 4B, контекст 4096. Реальный результат — `assisted`,
**208.44 с**, без повторной попытки и без fallback. Монолог совпал с удачным вариантом
ДТП из итоговой серии. [Ответ и метрики](prose-deployed-2cpu.json).

Это проверка одной генерации с обычными лимитами, не среднее время и не гарантия
для пакета. Качество проверяется дополнительным вызовом модели, поэтому генерация
теперь дороже по времени, чем прежний выбор трёх чисел. Для быстрой подготовки
остаётся явно выбранный режим заготовки без ИИ.

Рабочая БД не очищалась, seed не запускался, старые тексты не переписывались.
Готовность API, frontend и прокси проверена; перед миграцией сделана закрытая
резервная копия. Собственные контейнеры модели и тестовой БД удалены после проверок.
