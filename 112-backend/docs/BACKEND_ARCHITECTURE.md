# Архитектура backend

Актуально после декомпозиции 25.09.2026. Это модульный монолит FastAPI / SQLAlchemy;
HTTP API, схема БД и предметные правила при декомпозиции сохранены.

## Направление зависимостей

- `api`: HTTP-параметры, роли и зависимости доступа, ответы; вызов конкретного use case.
- `services`: прикладные команды, правила доступа к объектам, транзакции, чтение данных.
  Импорта роутеров или HTTP dependency-функций здесь нет.
- `schemas`: входные и выходные контракты, валидация формы данных.
- `models`: SQLAlchemy-модели и ограничения хранения.
- `db`: сессии, база моделей и небольшие SQL-помощники.
- `core`: настройки, безопасность, журналирование и независимые общие функции.
- `scripts`: явно выбранный HTTP-транспорт либо прямые вызовы сервисов.
  Скрипт не вызывает Python-функцию эндпоинта в обход HTTP-зависимостей.

`models`, `schemas`, `core`, `db` не импортируют сервисы и API. Сервисы не импортируют
API. Роутеры не импортируют друг друга для доступа к вспомогательным функциям:
сборка маршрутов находится только в `router.py` и пакетных `__init__.py`.
Параметры `Limit`, `Offset`, `Search` находятся в `api/pagination.py`.

В сервисах зависимости направлены в одну сторону, включая отложенные импорты.
Пакетные `__init__.py` сервисов не делают массовых реэкспортов; вызывающая сторона
импортирует модуль нужной операции. Это помогает видеть реальные зависимости.

## Основные области

| Область | Где находится | Ответственность |
| --- | --- | --- |
| Выполнение занятия | `services/student/access.py`, `attempts.py`, `creation.py` | Доступ, старт, снимок настроек и исходное состояние |
| Чтение работы | `services/student/journal.py`, `reads.py` | Журнал ученика, карточка и пакетный разбор попыток |
| Оператор 112 | `services/student/commands.py`, `routing.py` | Черновик, сдача, рекомендованные и выбранные службы |
| Подготовка материалов | `services/authoring/cards.py`, `scenarios.py`, `catalog_access.py` | Библиотека, версии/снимки сценариев, удаление/архивация, доступность справочников |
| ДДС | `services/dds/` | Инициализация, доступ к своей службе, чтение, команды службы и бригад |
| Подсказки | `services/learning_hints/` | Политика, задачи 112/ДДС, подтверждение свободного ввода, выдача и аудит |
| Сопровождение интерфейса | `services/interface_guide.py` | Последовательность объяснений и подтверждение шага |
| Формальная оценка | `services/automatic_assessment/` | Критерии, оценка попытки, итог урока, координация публикации |
| Смысловая оценка / RAG | `services/semantic_assessment/`, `assessment_memory/` | Сохранённый контекст, вызовы модели, проверка и применение результата |
| Рекомендации | `services/learning_recommendations/` | Профиль навыков, отбор методик и публикация рекомендаций |
| Сообщения | `services/messages.py` | Получатели, доступ, прочтение, отзывы и доступность ссылок на занятия |
| Прокторинг | `services/proctoring.py` | Приём наблюдений, идемпотентность, лимиты, история и мониторинг |
| Справочники | `services/catalog_admin.py`, `catalog_editor.py` | Создание, редактирование, проверка и публикация ЕКП |
| Телефония | `services/telephony/` | Рабочие места, звонки, адаптер АТС, медиа и отдельный worker |

`api/v1/activity/` разделён на группы, сообщения, профили учеников, отчёты,
аудит аккаунта и прокторинг. `api/v1/views/` группирует компактные read-only
представления по аккаунтам, учебным материалам, занятиям и справочникам.
Небольшие SQL-проекции могут оставаться в роутере: механический перенос каждой
строки SELECT в обёртку не даёт полезной границы ответственности.

## Транзакции и доступ

Команда сохраняет прежнюю последовательность проверок и блокировок. Коммит
остаётся у владельца операции. Чтение состояния, запись события и вычисление
оценки сами по себе не становятся отдельными транзакциями после переноса файла.

Особое правило: `student_lesson` проверяет принадлежность задания и **всегда**
блокирует урок, потому что затем исполняет сроки и поступление карточек ДДС.
Это не чистое чтение. Неиспользовавшийся аргумент `lock` удалён без изменения
блокировок. `owned_attempt(lock=True)` дополнительно обновляет попытку после
ожидания блокировки. Сроки фиксируются даже перед отклонением запоздалой команды;
нельзя без анализа заменить это одним внешним rollback всей HTTP-операции.

Роли остаются в API dependencies, владение конкретными объектами проверяется
сервисами. Seed вызывает те же проверки подготовки материалов, но административный
CLI-транспорт по-прежнему сам выбирает действующего администратора.

Учебный аудит и прокторинг остаются разными моделями и потоками. Общий
`audit.append_student_event` только задаёт доверенного исполнителя и вызывает
существующее выделение последовательности событий под блокировкой попытки.

## Устранённые циклы

- Оценка попытки не публикует итог урока сама: `assess_attempt` сохраняет критерии,
  `publish_lesson_result` агрегирует/восстанавливает недостающие оценки, а
  `assess_submission` координирует эти две операции. Восстановление не вызывает
  публикацию рекурсивно.
- `dds.views` читает службы и бригады, не импортируя команды их изменения.
  Команды могут возвращать это представление без обратной зависимости.
- Проверка свободного ввода и хеша подтверждения вынесена в
  `learning_hints.confirmation`; выбор задачи не импортирует весь workflow гайда.
- Канонический хеш JSON находится в `core/fingerprints.py`. Смысловая оценка и
  рекомендации больше не импортируют оркестрацию формальной оценки ради хеша.

Удалены повторная проверка ДДС в сдаче 112 и дублирование ограничений пагинации.
Локальные импорты сервисов подняты на уровень модулей после устранения циклов.
В worker разные `prepare`/`evaluate` вызываются через именованные модули своих
областей; выбор обработчика для трёх назначений задач проверяется тестами.

## Что намеренно не вводилось

- Универсальные Repository / UnitOfWork / классы UseCase: AsyncSession уже даёт
  единицу работы, а JOIN, блокировки и снимки требуют конкретных запросов.
  Обёртки над каждым методом SQLAlchemy сделали бы транзакции менее заметными.
- Микросервисы, шина событий, отдельная очередь или БД: они усложнили бы атомарность
  карточки, аудита и оценки. Тяжёлые операции уже исполняются worker-процессами.
- Собственная иерархия исключений ради замены каждого HTTPException. Сейчас этот
  тип используется и сервисами, и прямым CLI; дополнительный маппинг оправдан,
  когда появится потребитель, которому действительно нужен другой контракт ошибок.
- Лимит строк в файле как архитектурное правило. Например, жизненный цикл звонка
  и lease общего worker остаются цельными; размер сам по себе не причина дробления.

## Оставшиеся точки внимания

1. Блокировка урока сериализует часть команд разных учеников одной группы.
   Ослаблять её следует после измерения конкуренции и проверки инвариантов
   дедлайнов/поступления/итоговой оценки, а не в рамках переноса функций.
2. Старый `GET /student/lessons` вызывает `lesson_work` для каждого урока. Это
   ограниченный пагинацией, но всё же растущий по числу строк набор запросов.
   Основные списки используют `/views/*`; дальнейшая оптимизация требует
   отдельного измерения числа запросов и времени ответа.
3. Версионированные JSON-снимки — часть исторических результатов. Декомпозиция
   не повод удалять чтение старых опубликованных профилей ДДС или менять рубрику.
4. Время ожидания разных типов AIJob зависит от общего последовательного worker
   и CPU-модели. Приоритеты/раздельные воркеры — самостоятельное изменение
   эксплуатационного поведения, не архитектурная косметика.

## Проверки изменений

- Сравнение полного OpenAPI до и после: пути, operationId, параметры, схемы и
  описания ответов совпадают (122 пути).
- `tests/test_architecture.py`: направление зависимостей, отсутствие вызовов
  эндпоинтов из CLI, отсутствие циклов между сервисами, включая локальные импорты.
- `tests/test_worker_dispatch.py`: правильный выбор модели и подготовки контекста
  для генерации, оценивания и рекомендаций, без настоящего вызова модели.
- Существующие интеграционные тесты проверяют реальную PostgreSQL: права, ревизии,
  конкурентные команды, seed, дедлайны, асинхронное ДДС, подсказки и оценки.
- Перед коммитом обязателен полный pre-commit с pytest на отдельной мигрированной БД.

Декомпозиция не требует миграции, очистки данных или повторного seed. API/worker
нужно пересобрать, поскольку внутренние Python-пути изменились.
