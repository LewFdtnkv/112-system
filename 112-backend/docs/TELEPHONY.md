# Учебная телефония

Обновление 25.09.2026: [разговор ДДС с руководителем бригады](CREW_CALLS.md) —
приветствие, речь ученика, подтверждение, автоматическое завершение и оценивание.
Ниже сохранён общий контракт телефонии; для обязательных звонков действуют
уточнения нового документа.

Реализованы три режима рабочего места: `external` (существующая АТС и аппарат), `browser` (наш Asterisk и SIP.js/WebRTC), `phone` (наш Asterisk и SIP-аппарат). Системная роль ученика и учебная роль 112/ДДС от подключения телефона не меняются.

## Запуск локального Asterisk

В `.env` backend включите `TELEPHONY_ENABLED=true`, задайте случайный `ARI_PASSWORD` не короче 24 символов. Для демонстрации на одном компьютере остальные значения из `.env.example` можно оставить. Команда из `112-backend`:

```sh
docker compose --profile telephony up -d --build
```

Миграция `0021_telephony` применяется сервисом `migrate`. Данные существующих занятий не удаляются. Asterisk 22.11.0 собирается из официального исходного архива с проверкой SHA-256. Первоначальная сборка требует интернета; подготовленные образы работают локально. ARI доступен только внутри Docker-сети, через frontend проксируется только `/sip-ws`, не административный ARI. В dialplan нет транков, выхода в город, экстренных номеров или демонстрационных маршрутов Asterisk: разрешён только учебный номер `9000` после авторизации станции.

`asterisk` и `telephony-worker` запускаются отдельным профилем. Они ограничены 512 и 256 МБ соответственно, без загрузки языковой модели. API и работник используют общий том `telephony_media`; АТС монтирует его только для чтения. Очередь записей и команды звонков хранятся в PostgreSQL, дополнительный брокер не требуется.

Для телефона в локальной сети задайте `SIP_PUBLIC_ADDRESS` равным LAN IPv4-адресу компьютера с Docker, `SIP_BIND_ADDRESS=0.0.0.0`. Телефону нужны UDP 5060 и RTP UDP 10000–10100. Учётная запись, пароль и домен доступны администратору кнопкой «Настройки SIP». Используйте отдельные учебные аппараты/аккаунты. Доступность конкретного РТУ Т16Р и его прошивки нужно проверить на самом аппарате.

Оставьте `SIP_LOCAL_NET=auto`: при старте локальным считается только собственный IP контейнера Asterisk (/32), а SIP Contact и адрес RTP для клиентов через опубликованные порты заменяются на `SIP_PUBLIC_ADDRESS`. Не задавайте всю Docker-подсеть (например, `172.16.0.0/12`): Docker Desktop передаёт вызов с адреса шлюза этой подсети, и Asterisk ошибочно возвращает телефону недоступный адрес контейнера. Признаки: регистрация успешна, в ответе на звонок `Contact` и SDP `c=IN IP4` содержат `172.x`, звука нет, вызов обрывается примерно через 32 секунды из-за отсутствия ACK. Явная подсеть нужна только для специально настроенной сети без такого NAT. После изменения перезапустите Asterisk; обычного reload транспорта недостаточно.

Правило замены адресов описано в [документации Asterisk по NAT](https://docs.asterisk.org/Configuration/Channel-Drivers/SIP/Configuring-res_pjsip/Configuring-res_pjsip-to-work-through-NAT/). Проверка на локальном Docker Desktop 27.09.2026: отдельный SIP-клиент с хоста выполнил Digest-вход и вызов временного тестового номера; ответ содержал `Contact: sip:127.0.0.1:5060` и SDP `127.0.0.1`. Клиент получил аудио подготовленного приветствия и эхо отправленного RTP; повторных ответов 200 после ACK не было. Тестовый номер и endpoint удалены, попытки и оценки учеников при проверке не менялись. Это проверка сети и аудиотракта, а не микрофона пользователя или содержания речи.

Браузер на том же компьютере можно открывать по `http://localhost:8080`. Для других компьютеров необходим HTTPS с доверенным сертификатом (браузер требует защищённый контекст для микрофона); reverse proxy должен передавать `/sip-ws` с Upgrade. Относительный `TELEPHONY_WS_URL=/sip-ws` автоматически становится `ws:` или `wss:` по схеме страницы. Для публикации UI в LAN предусмотрен `FRONTEND_BIND_ADDRESS`. Тестовый флаг Chromium, разрешающий микрофон на HTTP, предназначен только для автоматических испытаний и не используется приложением.

## Работа пользователя

1. Администратор открывает «Телефонные рабочие места», создаёт станцию, выбирает режим, SIP-логин и ученика. У одного ученика одно закреплённое место; переключить/отключить его во время звонка нельзя.
2. Преподаватель открывает «Записи звонков», выбирает сценарий. Для 112 исходный текст берётся из сообщения заявителя, для ДДС — из сообщений задания и контактов опубликованного профиля. Преподаватель может подготовить отдельную реплику для каждого контакта. Скрытые эталонные ответы не передаются генератору автоматически.
3. Загрузите WAV PCM: моно, 8000 Гц, 16 бит, 0,1–600 секунд, до 10 МБ. Можно прослушать запись перед занятием. Например, преобразование заранее подготовленного файла:

```sh
ffmpeg -i source.wav -ac 1 -ar 8000 -c:a pcm_s16le lesson.wav
```

4. Ученик открывает карточку и подключает рабочее место. В браузере разрешает микрофон, затем нажимает «Позвонить» либо «Вызвать меня» и «Принять». На физическом аппарате после выбора контакта набирает `9000`; кнопка «Вызвать меня» звонит на закреплённый аппарат. Для внешней АТС используются её настроенные учебные контакты и адаптер.
5. Соединение, ответ и завершение поступают с АТС. Нажатие «Позвонить» само по себе не означает состоявшийся разговор. История доступна в карточке и в аудите занятия преподавателя. Действия звонка не меняют статусы служб или бригад и сами по себе не задают итоговую оценку.

Поддерживается воспроизведение готовой речи. Свободный диалог, распознавание ответа ученика и TTS-модель в эту итерацию не входят. Входящий звонок сейчас запускается явной кнопкой; расписание автоматических событий может вызывать тот же прикладной процесс позже. При закрытии АРМ браузер отключает SIP и медиапотоки; физический телефон независим от вкладки. При окончании занятия локальный работник завершает его активные звонки.

## Подготовка аудио и контракт генератора

При назначении сценария заранее создаются реплики и задания подготовки. Открытие экрана записей также подготавливает ранее назначенные сценарии. Ключ кэша зависит от текста, голоса и версии генератора. Одинаковые тексты повторно не синтезируются; готовые WAV нормализуются и адресуются по SHA-256. Загрузка новой записи создаёт новую версию, уже начатый звонок использует прежнюю. Звонок через локальную АТС запрещён, пока файл не готов и не доступен на диске.

Генератор — отдельный доверенный процесс. Он может использовать локальную TTS или заранее подготовленные нейросетью записи. В запросах нужен `X-Generator-Token`, значение `SPEECH_GENERATOR_TOKEN`. Пользовательский JWT его не заменяет. Базовый путь `/api/v1/telephony-adapter`:

- `POST /speech/claim`: атомарно получить одну реплику; `null`, если очереди нет. Ответ содержит `id`, `text`, `voice`, `generator_version`, требования `output`, `lease_token`, `leased_until`.
- Генерация идёт вне HTTP запроса и транзакции БД. Аренда 10 минут; `POST /speech/{id}/renew?lease_token=...` продлевает её для длительного синтеза.
- `PUT /speech/{id}/wav?lease_token=...`: двоичное тело WAV. Устаревший токен получает 409; поздний результат предыдущего работника не заменит актуальный.
- `POST /speech/{id}/failed`: JSON `{"lease_token":"...","error":"Краткое описание"}`. До трёх попыток; после этого явная ошибка. Повторную подготовку преподаватель запускает сохранением реплики.

Без генератора задания остаются в ожидании: не создаётся тишина или фиктивный успешный результат. Преподаватель может загрузить файл вручную. Завершённые записи и данные очереди не требуют постоянно работающей TTS или LLM. Сначала LLM готовит согласованный текст по фактам карточки, затем TTS превращает этот текст в запись; эти этапы не выполняются при поднятии трубки.

## Контракт внешней АТС

Конкретный производитель пока неизвестен. Нужен адаптер на стороне доверенного контура АТС: AMI/ARI, vendor API или событийный журнал. Наличие одного SIP-телефона и Caller ID недостаточно для достоверной регистрации разговора backend. Прослушивание чужого SIP-трафика браузером не используется.

Администратор создаёт станцию `mode=external`, `provider=<код адаптера>`, `endpoint=<стабильный идентификатор телефона АТС>`. Адаптер использует `X-Adapter-Token` из `TELEPHONY_ADAPTER_TOKEN`, без пользовательской сессии. Рекомендуется передавать события по HTTPS либо внутри изолированной сети, хранить исходящие события в устойчивой очереди до HTTP 200.

- `GET /pbx/{provider}/stations/{endpoint}`: текущая привязка к `attempt_id`, `student_id`, подготовленный `pending_call` и разрешённые контакты. Это доверенный API адаптера; SIP-пароли не возвращает.
- `POST /pbx/{provider}/events`: нормализованное событие, пример ниже. `provider_call_id` объединяет все технические каналы одного учебного разговора, например Asterisk Linkedid с учётом перевода/второго плеча. `event_id` стабилен при повторах.
- Если звонок подготовлен в UI, укажите его `call_id`. Если ученик набрал на аппарате без нажатия кнопки в браузере, передайте `attempt_id`, полученный **в момент начала звонка**, и `contact_key` из разрешённых контактов. Смена привязки не должна приписывать запоздалые события другому занятию. После первого ответа сохраняйте возвращённый `id` и используйте его как `call_id` для следующих событий.
- `GET /pbx/{provider}/calls/{call_id}/wav`: получить готовую реплику, если она есть. Проигрывание в существующей АТС реализует её адаптер, поскольку vendor API неизвестен. Backend не считает файл воспроизведённым только по факту скачивания.

```json
{
  "event_id": "stable-event-124",
  "endpoint": "arm-01",
  "provider_call_id": "linked-call-42",
  "attempt_id": "UUID из привязки в момент начала",
  "contact_key": "crew",
  "direction": "outgoing",
  "kind": "connected",
  "occurred_at": "2026-09-23T12:00:00Z"
}
```

Состояния: `dialing`, `connected`, `ended`, `busy`, `no_answer`, `failed`. `connected` означает соединение учебных сторон, а не только ответ первого аппарата в многоплечевом вызове. Дубликаты не создают новые события оценки. События сохраняются в `telephony_events`; итог вычисляется с учётом времени, позднее `dialing` не открывает завершённый разговор. Неизвестные телефоны/контакты и конфликтующие ID отклоняются. События неучебных звонков не отправляются в тренажёр. До первого события АТС ученик может отменить выбор контакта; подтверждённый звонок завершается на аппарате; обещания управления неизвестной АТС нет.

## Надёжность и границы

Единственный активный `telephony-worker` выбирается advisory lock PostgreSQL. Доступ к станции сериализует создание звонков; повтор команды с тем же UUID возвращает прежний звонок. До внешнего вызова сохраняется детерминированный ARI channel ID. При неопределённом сетевом результате работник проверяет канал и не звонит повторно. После переподключения ARI активные каналы сверяются с БД. Пропавший канал отмечается технической ошибкой; ошибка инфраструктуры не трактуется как ошибка ученика. Ожидание набора ограничено 60 секундами, ответ аппарата — 45, общая длительность по умолчанию — 600.

Таблицы: `telephony_stations` (привязка), `call_cues` (реплики карточек), `speech_assets` (кэш/очередь), `training_calls` (попытка, контакт, направление, времена), `telephony_events` (первичные события). Семантические `call.*` попадают в `attempt_events`, отдельно от прокторинга. Запись речи ученика в файл, ASR и содержательное оценивание разговора не включены; сейчас фиксируются жизненный цикл звонка и воспроизведение подготовленной реплики.

Основные источники: [ARI](https://docs.asterisk.org/Configuration/Interfaces/Asterisk-REST-Interface-ARI/), [WebRTC/PJSIP](https://docs.asterisk.org/Configuration/WebRTC/Configuring-Asterisk-for-WebRTC-Clients/), [динамическая настройка PJSIP](https://docs.asterisk.org/Configuration/Interfaces/Asterisk-REST-Interface-ARI/The-Asterisk-Resource/ARI-Push-Configuration/), [приём звонков SIP.js](https://sipjs.com/guides/receive-call/).

## Выполненные проверки (23.09.2026)

- Чистая PostgreSQL: upgrade до 0021 и `alembic check`, схема совпадает с моделями. Полная регрессия — 266 тестов.
- Реальный Asterisk: исходящий и входящий SIP.js/WebRTC, приём RTP-аудио проверен по ненулевой амплитуде тестовой записи.
- Независимые программные SIP-клиенты по UDP: исходящий звонок (siprobo), входящий с приёмом RTP (pyVoIP). Это проверка протокола режима phone, не испытание физического РТУ.
- Создание/привязка станции, загрузка/предпрослушивание WAV, дедупликация и порядок событий, аренда генератора и неизменность аудио активного звонка. Внешняя АТС проверена через контракт API; конкретный vendor-адаптер ещё предстоит реализовать после выбора АТС.
- Frontend: FSD, lint, production build, 136 тестов; скриншоты в `112-frontend/docs/screenshots/telephony/`.

Повторная сквозная проверка браузера: `112-frontend/scripts/check-telephony.mjs`, запускать Node только в Docker с установленными зависимостями проекта и Chromium Playwright. Переменные окружения:

- `PLAYWRIGHT_BASE_URL`: адрес тестового frontend с API и `/sip-ws`.
- `PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH`: путь Chromium в образе.
- `TELEPHONY_FIXTURE`: путь к локальному JSON внутри контейнера: `{"usernames":{"student":"..."},"password":"...","lesson":"UUID"}`. Файл с тестовыми реквизитами не коммитить.
- `TELEPHONY_ALLOW_TEST_HTTP=1`: только для изолированного HTTP-стенда, никогда для рабочего окружения.

Предусловия: незавершённая карточка ДДС, назначенная browser-станция, запущенный worker и Asterisk, подготовленная запись контакта (для проверки звука — тестовый тон 440 Гц длительностью 5 секунд). Скрипт проходит UI, проверяет исходящий и входящий звонки и сохраняет скриншоты. Проверки не требуют изменения рабочей БД.
