# Числовая валидация HTTP API

Исправления по `audit/NUMERIC_AUDIT.md` (A-03/A-04, 25.09.2026).

## Причины ошибок

- Python принимает целые произвольной длины, а PostgreSQL/asyncpg принимает OFFSET
  в диапазоне signed int64. Общий Offset и три отдельных объявления не имели
  верхней границы. `after` сравнивается с SQL INTEGER, поэтому ему нужен int32.
- Стандартный JSON-декодер Python принимает NaN/Infinity и превращает `1e309`
  в бесконечность. Pydantic отклоняет такой пароль или координату, но стандартная
  сериализация ответа об ошибке повторяла неконечное число в `detail[].input` и
  сама падала. Произвольные JsonValue также пропускали его к сериализации JSONB.

## Текущие правила

| Данные | Ограничение |
|---|---|
| `limit` | 1…100, без изменения |
| `offset`, `active_offset` | 0…9 223 372 036 854 775 807 (signed int64) |
| `after`, `through` | 0…2 147 483 647 (INTEGER последовательности событий) |
| Входные `revision`, `expected_revision` | целое до 2 147 483 647; нижняя граница прежняя (1 либо 0); строки, bool и float не приводятся к целому |
| JSON-тела моделей API | NaN, ±Infinity, ±1e309 и вложенные неконечные числа → 422 |
| Новые JSON-данные карточки и значения наблюдений | конечные числа с модулем ≤9 007 199 254 740 991 (2^53−1); ограничения известных предметных полей также действуют |

Последнее правило защищает браузерный обмен от заведомо непредставимых целых и
чрезмерных величин, но не обещает точное десятичное представление float.
Большой идентификатор, телефон или номер дома должен передаваться строкой.
Строки `"1e309"`/`"NaN"` не переписываются в числа и сами по себе не запрещены.
Старые сохранённые конечные значения остаются читаемыми; миграции/перезаписи БД нет.

Общий dependency проверяет уже разобранные тела моделей до выполнения команды.
Он не перехватывает потоки файлов: импорт ЕКП сохраняет свой лимит 8 MiB и
строгую схему, WAV/фото — существующие обработчики. Это не новый лимит размера
для произвольных HTTP-тел и не общий механизм защиты от нагрузки.

Обработчик RequestValidationError возвращает 422 с `detail[].type`, `loc`, `msg`.
`input` и `ctx` не возвращаются: ошибки не повторяют пароль/тело запроса и не
срывают JSON-сериализацию из-за неконечного диагностического значения.
Прочие ошибки приложения не превращаются этим обработчиком в 422.

## Проверки

`tests/test_numeric_validation.py` проверяет все GET-параметры
`offset/active_offset/after/through` из актуальной OpenAPI: превышение предела,
1000 цифр и отрицательное значение. Вместо БД в этом проходе стоит объект,
который немедленно падает при обращении: некорректный ввод не доходит до SQL.

Отдельно проверены настоящие HTTP-запросы с пятью видами неконечных чисел:
публичный login, координаты, score/max_score, вложенный JSON карточки;
разные JSON Content-Type, безопасная выдача ошибок, ограничения ревизий,
свободные JSON-поля и прежний лимит импорта.

Интеграция на отдельной PostgreSQL проверяет отсутствие изменения карточки,
ревизии и учебных событий при отказе, допустимый OFFSET=int64_max и успешную
запись корректной карточки после неудачных запросов. Остальные роли и учебные
переходы проверяются полным существующим набором pytest.
