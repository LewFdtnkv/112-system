# Backend «Система-112»

FastAPI · SQLAlchemy (asyncpg) · PostgreSQL 17 · Alembic · Docker Compose · uv.

Бригады ДДС: настройка в профиле службы, ручное назначение, независимая история и
автоматическая проверка целей — [описание и API](docs/DDS_CREWS.md). Миграция `0016_dds_crews`
сохраняет существующие задания и оценки.

Все команды выполняются из `112-backend`. Нужны **uv** и **Docker Compose**; Python 3.13 выбирается через `.python-version`.

## Первая настройка

```bash
test -f .env || cp .env.example .env
uv sync --locked
uv run pre-commit install
uv run python -c 'import secrets; print(secrets.token_urlsafe(48))'
```

Записать сгенерированное значение в `JWT_SECRET_KEY` в локальном `.env`. Секрет должен содержать не менее 32 символов и быть одинаковым у всех процессов API. Готового общего секрета в проекте нет; API без него не запускается. Не коммитить `.env`. Остальные параметры перечислены в `.env.example`.

### API локально, БД в Docker

```bash
docker compose up -d --wait db
uv run alembic upgrade head
uv run uvicorn app.main:app --reload
```

Если контейнерный API уже запущен, сначала освободить порт: `docker compose stop api`.

### Весь Compose

```bash
docker compose up --build -d --wait
```

Для генерации карточек один раз загрузите локальную модель:
`docker compose exec llm ollama pull qwen3:4b-instruct-2507-q4_K_M`.
Compose также запускает `llm` и отдельный `worker`; очередь хранится в PostgreSQL.
Настройки, ограничения памяти и API: [Генерация карточек](docs/CARD_GENERATION.md).

Swagger: <http://localhost:8000/docs>. PostgreSQL на хосте: `localhost:15432`; внутри Compose: `db:5432`.

Фронтенд: <http://localhost:8080> (порт задаётся через `FRONTEND_PORT`). Сервис
`frontend` собирается из соседней папки `../112-frontend`, которая должна быть
доступна при сборке. Nginx раздаёт статику, поддерживает прямые ссылки на страницы
и проксирует `/api/` в `api:8000`, сохраняя путь запроса.

## Пользователи и права

`users`: UUID, уникальный логин `username`, хеш пароля Argon2, имя, фамилия, необязательные отчество и email, `is_active`, `is_teacher`, `is_admin`, `must_change_password`, даты создания, обновления, последнего входа и смены пароля. Логин нормализуется в нижний регистр; допустимы латинские буквы, цифры, `_`, `-`, `.`. Email — необязательный контакт, не идентификатор входа.

Системные роли взаимоисключающие: ученик, преподаватель или администратор. API принимает `role`; совместимые флаги `is_teacher` и `is_admin` ограничены CHECK в БД (оба `false` — ученик). Только администратор создаёт и редактирует аккаунты, отключает доступ; изменение активности отзывает сеансы. Роль выбирается только при создании и не меняется: для другой роли создаётся отдельный пользователь. Преподаватель ведёт свои группы и уроки. Учебная роль 112/ДДС назначается отдельно. См. [управление аккаунтами](docs/USER_ADMINISTRATION.md) и [предварительную автопроверку](docs/AUTOMATIC_CHECK.md).

| Метод и путь (префикс `/api/v1`) | Доступ / назначение |
| --- | --- |
| `POST /auth/login` | Вход: JSON `username`, `password` |
| `POST /auth/refresh` | Обновление пары: JSON `refresh_token` |
| `POST /auth/change-password` | Access-токен + JSON `current_password`, `new_password` |
| `POST /auth/logout` | Access-токен; отзыв текущей сессии, ответ `204` |
| `GET /users/me` | Собственный профиль после обязательной смены пароля |
| `GET /users?limit=20&offset=0` | Преподаватель или администратор; `limit` от 1 до 100 |
| `GET /users/{user_id}` | Преподаватель или администратор; `404`, если пользователя нет |
| `POST /users` | Только администратор; новый аккаунт с обязательной сменой стартового пароля |

Защищённые запросы принимают `Authorization: Bearer <access_token>`. В Swagger получить токен через `/auth/login`, затем вставить **access-токен** в `Authorize`. Пароли, их хеши и сведения о токенах в профили не попадают. `/health/live`, `/health/ready` и документация доступны без авторизации.

### Первый вход `admin:admin`

Начальная миграция создаёт активного администратора с `is_admin=true`, `is_teacher=false`, `must_change_password=true`. В БД сохраняется только хеш стартового пароля со случайной солью.

1. `POST /api/v1/auth/login` с `{"username":"admin","password":"admin"}` возвращает `access_token`, `refresh_token`, `token_type`, `expires_in` (секунды) и `must_change_password: true`.
2. Клиент должен показать форму смены пароля. До смены **все прикладные ручки, включая `/users/me`, отвечают `403` с `detail: "password_change_required"`**. Разрешены операции авторизации: вход, refresh, смена пароля и выход. Refresh сохраняет ограничение.
3. `POST /api/v1/auth/change-password` с Bearer access-токеном и `{"current_password":"admin","new_password":"новый пароль"}`. Новый пароль — от 12 до 128 символов, не состоит только из пробелов и отличается от текущего. Пробелы в пароле не обрезаются.
4. Смена пароля возвращает новую пару токенов с `must_change_password: false`. **Все прежние сессии этого пользователя, включая текущую, отзываются**. Клиент должен заменить оба токена полученными. Стартовый пароль больше не действует.

Требование смены пароля проверяется сервером по БД и применяется к любому пользователю с установленным флагом. Фронтенд в этой задаче не изменён; показ формы нужно подключить к этому контракту.

### Сессии и токены

- Access — JWT HS256 с проверкой подписи, срока действия, issuer, audience, типа и идентификаторов пользователя/сессии. По умолчанию действует 15 минут (`ACCESS_TOKEN_MINUTES`). Права не копируются в JWT: активность пользователя, флаги доступа и состояние сессии проверяются по БД при каждом защищённом запросе.
- Refresh — криптографически случайный непрозрачный токен. Таблица `auth_sessions` хранит только SHA-256 хеш. Срок сессии — 7 дней (`REFRESH_TOKEN_DAYS`), считается от входа и не продлевается при refresh.
- Каждый refresh заменяет токен новым. Предыдущий повторно не принимается. Конкурирующие запросы сериализуются блокировкой строки пользователя: один refresh нельзя успешно использовать дважды. Старый access остаётся действительным до своего истечения или отзыва сессии.
- Logout отзывает текущую сессию вместе с её access и refresh. Смена пароля отзывает все сессии. Неактивные и удалённые пользователи не могут входить и использовать ранее выданные токены.
- Хеширование и проверка Argon2 выполняются в пуле потоков, чтобы не блокировать цикл обработки async-запросов. Ответы с токенами имеют `Cache-Control: no-store`.

## Группы, карточки, сценарии и запуск урока

Все операции ниже требуют `is_teacher=true` и сменённого стартового пароля.
Преподаватель видит и использует только свои группы, карточки, сценарии и уроки;
чужой объект возвращает `404`. Администратор без флага преподавателя получает `403`.

| Метод и путь (префикс `/api/v1`) | Назначение |
| --- | --- |
| `POST /groups` | Создание группы: `{"name":"Группа 1"}` |
| `GET /groups`, `GET /groups/{id}` | Свои группы |
| `PUT /groups/{id}/students/{student_id}` | Добавление активного ученика; повтор безопасен, ответ `200` |
| `GET /groups/{id}/students` | Состав группы |
| `POST /cards`, `GET /cards`, `GET /cards/{id}` | Библиотека ручных карточек преподавателя |
| `POST /scenarios`, `GET /scenarios`, `GET /scenarios/{version_id}` | Сценарии из упорядоченных карточек |
| `POST /lessons/start` | Запуск выбранной версии сценария для своей группы |
| `GET /lessons`, `GET /lessons/{id}` | Уроки и количество учеников/назначений |
| `GET /lessons/{id}/assignments` | Назначения в порядке ученика и `position`; фильтр `student_id` |
| `GET /classifiers` | Опубликованные версии ЕКП |
| `GET /classifiers/{id}/entries` | Коды выбранной опубликованной версии |
| `GET /classifiers/{id}/entries/{entry_id}/routes` | Получатели и условия оповещения по коду |
| `GET /services`, `GET /service-profiles?service_id=...` | Активные службы и опубликованные профили |

Списки принимают `limit=20&offset=0`, максимум 100 записей; список маршрутов кода возвращается целиком.
Контракт и пример цепочки запросов: [docs/TEACHER_API.md](docs/TEACHER_API.md).

**Нужна подготовленная опубликованная версия ЕКП с кодами и маршрутами служб.**
Ручные карточки и новые уроки без неё недоступны. Администратор может подготовить
справочник с простыми безусловными маршрутами через `POST /admin/services`,
`POST /admin/classifiers` и `POST /admin/classifiers/{id}/publish`.
Импорт исходных XLSX пока не реализован. Для ДДС нужен опубликованный профиль активной службы.
Для запуска урока одному участнику группы передать `student_id` в `/lessons/start`.

Сценарий фиксирует снимки карточек. Запуск атомарно создаёт активный урок и
назначения всех карточек всем текущим ученикам группы, с порядком `position`.
Повтор запуска с тем же `request_id` возвращает прежний урок; изменённые параметры — `409`.
Для роли оператора 112 реализованы ученический старт, черновик, расчёт получателей,
оповещение, последовательный переход к следующей карточке, автоматический итог и пересмотр преподавателем:
[docs/STUDENT_WORKFLOW.md](docs/STUDENT_WORKFLOW.md).
При запуске преподавателем таймеры попыток не стартуют. Выполнение ДДС описано в
[docs/CATALOG_AND_DDS.md](docs/CATALOG_AND_DDS.md), локальная генерация карточек —
в [docs/CARD_GENERATION.md](docs/CARD_GENERATION.md). SIP пока не подключён.

## Миграции

История переорганизована: **`0001_users` — новая начальная миграция**. Удалены демонстрационные `workstations`, их API, модель, схемы, тесты и старая ревизия `0001`. Новая ревизия намеренно имеет другой идентификатор: старая БД не должна ошибочно считаться актуальной.

Для новой пустой БД достаточно `uv run alembic upgrade head`. Если в существующей БД уже записана старая ревизия `0001`, эта история к ней неприменима. Сохранить нужные данные и создать отдельную пустую БД, направить на неё `DATABASE_URL` (при Compose также `POSTGRES_DB`), затем выполнить миграцию. Существующую БД и Docker volume эти изменения автоматически не удаляют. Команда `alembic stamp head` не создаёт таблицы и не заменяет перенос. Откат новой миграции до `base` удаляет пользователей и сессии; применять только там, где эти данные можно потерять.

Следующие изменения оформлять новыми ревизиями, не переписывая применённые миграции:

```bash
uv run alembic upgrade head
uv run alembic revision --autogenerate -m "add field"
# Проверить сгенерированный файл, особенно удаления и переименования.
uv run alembic upgrade head
uv run alembic check
```

## Проверки

```bash
uv run --locked ruff check
uv run --locked ruff format --check
uv run --locked pytest -q
```

Без `TEST_DATABASE_URL` интеграционные тесты **пропускаются**. Для полного набора использовать отдельную PostgreSQL с применёнными миграциями и неизменённым стартовым `admin:admin`. Большинство тестов откатывает транзакции; проверки конкурентности используют отдельные соединения и удаляют свои данные после завершения.

Пример временной БД, без обращения к данным проекта:

```bash
docker run --detach --rm --name system112-auth-test \
  --env POSTGRES_PASSWORD=auth-test --env POSTGRES_DB=auth_test \
  --publish 127.0.0.1:15433:5432 postgres:17
# Дождаться готовности: docker exec system112-auth-test pg_isready -U postgres
DATABASE_URL=postgresql+asyncpg://postgres:auth-test@127.0.0.1:15433/auth_test uv run --locked alembic upgrade head
TEST_DATABASE_URL=postgresql+asyncpg://postgres:auth-test@127.0.0.1:15433/auth_test uv run --locked pytest -q
DATABASE_URL=postgresql+asyncpg://postgres:auth-test@127.0.0.1:15433/auth_test uv run --locked alembic check
docker stop system112-auth-test
```

Проверяются авторизация и смена пароля, создание аккаунтов, права и изоляция преподавателей,
группы, опубликованный ЕКП, ручные карточки, снимки сценариев, оба вида урока,
порядок назначений и конкурентные запросы запуска/членства/создания пользователей.

## Разработка

- `app/api/v1/` — HTTP-обработчики; `schemas/` — контракты; `models/` — ORM; `services/` — авторизация и прикладные операции; `core/` — настройки и криптографические функции; `db/` — подключение.
- Новые модели импортировать в `app/models/__init__.py`. **Новые прикладные routers подключать к `protected_router` в `app/api/v1/router.py`**, чтобы обязательная смена пароля действовала для всех.
- Дополнительные слои repository и универсальная система ролей пока не нужны. Флаги покрывают текущую матрицу; отдельные разрешения можно вводить при появлении действительно разных административных операций.
- Зависимости менять через `uv add` / `uv add --group dev`, сохранять `pyproject.toml` и `uv.lock` вместе. После получения изменений — `uv sync --locked`.
- Не коммитить `.env`, `.venv/`, `.uv-cache/` и временные результаты. Перед коммитом проверять diff и добавлять файлы адресно.

Pre-commit запускает Ruff, проверку lock-файла, YAML/TOML, маркеров конфликтов, размеров файлов, пробелов и концов строк. При изменении Python, миграций или зависимостей выполняется pytest. Ручной запуск: `uv run pre-commit run --all-files`. Без `TEST_DATABASE_URL` этот запуск также не проверяет интеграцию с PostgreSQL.
