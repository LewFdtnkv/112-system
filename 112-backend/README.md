# Backend «Система-112»

FastAPI · SQLAlchemy (asyncpg) · PostgreSQL 17 · Alembic · Docker Compose · uv.

Все команды выполняются из `112-backend`. Нужны **uv** и **Docker Compose**; Python 3.13 выбирается через `.python-version`.

## Основные команды

### Первая настройка

```bash
test -f .env || cp .env.example .env
uv sync --locked
uv run pre-commit install
```

### Разработка: API локально с автоперезагрузкой, БД в Docker

```bash
docker compose up -d --wait db
uv run alembic upgrade head
uv run uvicorn app.main:app --reload
```

Если контейнерный API уже запущен, сначала освободить порт: `docker compose stop api`.

### Поднять весь Compose

```bash
docker compose up --build -d --wait
```

Swagger: <http://localhost:8000/docs>. PostgreSQL на хосте: `localhost:15432`; внутри Compose: `db:5432`.

### Создать и применить миграцию

После изменения ORM-моделей, при запущенной БД:

```bash
uv run alembic upgrade head                            # Применить существующие миграции
uv run alembic revision --autogenerate -m "add field"  # Создать новую
# Проверить сгенерированный файл перед применением
uv run alembic upgrade head
uv run alembic check                                   # Проверить соответствие схемы моделям
```

## Как вести проект

- **Структура:** `app/api/v1/` — HTTP-обработчики, `schemas/` — входные и выходные данные, `models/` — ORM, `db/` — подключение, `core/` — настройки. Бизнес-логику по мере появления выносить в `app/services/`; обработчики оставлять короткими.
- **Новый модуль:** модель импортировать в `app/models/__init__.py`, router подключить в `app/api/v1/router.py`. Опираться на пример `workstations`.
- **Миграции:** изменения схемы оформлять через Alembic вместе с изменениями моделей. Проверять `autogenerate` вручную, особенно удаления и переименования. Уже применённые в общей среде миграции не переписывать — добавлять новые.
- **Зависимости:** добавлять через `uv add <package>` или `uv add --group dev <package>`. Коммитить `pyproject.toml` и `uv.lock` вместе; после получения изменений выполнять `uv sync --locked`.
- **Настройки:** секреты хранить в `.env`, новые параметры описывать в `.env.example`. `.env`, `.venv/` и кэш `.uv-cache/` не коммитить. Кэш uv находится внутри backend.
- **Проверки:** для новой логики добавлять тесты успешных и ошибочных сценариев. Интеграционные тесты запускать на отдельной мигрированной PostgreSQL, заданной через `TEST_DATABASE_URL`; без неё они пропускаются.
- **Git / PR:** одна задача — одна ветка; небольшие коммиты с понятным описанием. В PR указывать, что изменилось, как проверено и есть ли изменения схемы или настроек. Обновлять документацию при изменении команд и API.

## Pre-commit

После клонирования установить Git-хук: `uv run pre-commit install`.

При коммите автоматически выполняются `ruff check --fix`, `ruff format`, проверка lock-файла, YAML/TOML, маркеров конфликтов, размера файлов (до 1 МиБ), исправление пробелов и концов файлов. При изменении Python-кода, миграций или зависимостей запускается `pytest`.

Ручной запуск на всех отслеживаемых файлах:

```bash
uv run pre-commit run --all-files
```

Если хук исправил файлы, проверить изменения, снова добавить их через `git add` и повторить коммит. Без `TEST_DATABASE_URL` интеграционные тесты пропускаются. Все инструменты хуков берутся из окружения uv и зафиксированы в `uv.lock`.

Каркас содержит пример API рабочих мест; аутентификация и привязка телефонов ещё не реализованы.
